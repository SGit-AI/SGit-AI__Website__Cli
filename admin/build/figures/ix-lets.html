Indexes in the pack, in LETS terms: load, extract, transform, save

Measured on a vault of 76,000 files and 58,062 folders (134,092 objects). Today a clone unpacks every object and every reader rebuilds what the pusher already knew. Proposed: the pusher ships its indexes beside the pack, the reader downloads them and assembles a local database. Dashed boxes are proposals; nothing in them is built.

Load

the network
2.4 MB

the whole head's index (every path, blob, size, hash, folder id), deflated; 17.2 MB as JSON

one folder of the vault
  • index pack, then 1 ranged read if blobs are stored in path order
  • 265 ranges for the same 1,520 files in today's id order

Extract

read in place, verify on first read
5 µs

to read one object out of the pack by offset (warm cache)

against today
  • 11.6 s to write all 134,092 objects loose on a fast disk; the newsroom's cloud disk took minutes
  • the pack's own directory: 10.7 MB, parsed in 0.56 s

Transform

JSON members into SQLite, locally
0.32 s

to assemble one head into SQLite (0.88 s for two heads)

queries on it
  • one path: 0.007 ms
  • a folder of 7,600 files: 5.4 ms
  • what changed between two heads: 58 ms

Save

a cache, losable, rebuilt from the packs
15 ms

to load the 26 MB database into memory from bytes (Python 3.11's deserialize)

so under sealed keys
  • keep it encrypted on disk and open it in memory per command
  • no new dependency: sqlite3 is in the standard library
Ship JSON, assemble SQLite: a SQLite file of the same index is the same size deflated (2.41 against 2.42 MB) and costs 0.32 s to build, so shipping the binary saves nothing here.
Ship the database when building it is the cost: a full-text index of the vault's 13 MB of text took 11.3 s to build from files a reader would first have to download; built, it is 2.4 MB deflated and answers in 0.2 ms.
What stays: a working clone still writes its working files and stats them on every scan. A reader that only needs to read pays the download and the queries.
