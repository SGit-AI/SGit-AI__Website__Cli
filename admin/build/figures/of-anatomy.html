A vault in one file: what goes in, and what must stay out

The file is the vault's bare/ folder, zipped as it is: every immutable object, and the few mutable pointers frozen at the moment the file was made. Counted from the newsroom's synthetic-users vault, a published vault, on 21 October 2026: 111 files, 12.7 MB as one stored zip. The clone's own local/ folder holds its credentials and must never go in.

vault.zip, the bare/ folder

bare/ data/ obj-cas-imm-… 106 blobs, trees, commits keys/ key-rnd-imm-… 2 public keys refs/ ref-pid-muw-… 1 the named branch's head ref-pid-snw-… 1 a clone branch's head indexes/ idx-pid-muw-… 1 the branch index cache/ 0 (optional, derived)

imm108 files that never change: any copy of them is as good as any other.
muwsnw3 files that say where the history is. Frozen in the file, they make it a read-only snapshot of the vault at that moment.

Never in the file: .sg_vault/local/

This clone's own state, keys included: a read-only clone keeps its read key in clone_mode.json, a writable clone its vault key in vault_key. The file carries ciphertext only; the key travels separately, or sealed inside an envelope (next figure).

Read it back

Unzip anywhere, then sgit clone --transport local --base-url <folder> <read key>. Measured: 0.48 s, the same working tree and the same three commits as a clone from the hosted server, which took 13.7 s.
