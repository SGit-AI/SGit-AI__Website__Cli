What the place that stores it can see, in each shape

The contents are encrypted in all three; no host reads a file, a filename or a commit message. What differs is the metadata around the ciphertext. A sealed file is one opaque blob; a plain zip carries its own directory; a vault on a server is many objects, fetched one request at a time.

A vault on a server, loose

  • sees the vault id
  • sees how many objects, and each one's size
  • sees which objects each reader fetches, and when
  • not names, contents, messages

Good for: many writers, compare-and-swap, partial clones.

One zip on Drive, Dropbox or S3

  • sees one file and its size
  • can read the zip's directory: the object ids, their sizes, the folders
  • sees who downloads the file, not which parts are read, unless by Range
  • not names, contents, messages

Good for: read-mostly vaults, one writer, storage that prefers big files.

The same zip, sealed to a public key

  • sees one file and its size
  • not the object count, ids or sizes
  • not even which vault it is
  • not names, contents, messages

Good for: handing a whole vault to one person or agent. The cost: it must be opened whole, so no reading one part by Range.
