Where sgit does less work than git, and where git is faster

Not a race: git reads plaintext, sgit decrypts everything it touches and its server can read nothing. The left column is where sgit's design means less work for the job; the right is where git is quicker today, said as plainly.

sgit does less

4.4 s vs 16.1

Large binary files. 40 files of 3 MB: a full sgit clone against a full git clone of the same files from local disk, which spends its time compressing what cannot be compressed.

3 MB of 527

One folder of a big vault, with no server-side support needed: --path --depth 1 fetches the spine to one folder, 13 s hosted.

0 requests

Caching anywhere. Every object is named by the hash of its ciphertext; a browser, a CDN or a CI cache keeps it for ever without being told. A reload inside two minutes fetches nothing.

any GET host

No server to run for readers. S3, GitHub Pages, a folder, one zip: a clone from a local folder took 0.48 s.

1.9 s for 10

Many agents at once. Scoped clones barely load the server; the work is on the clients.

git is faster

0.4 s

git's own partial clone with a sparse checkout, from local disk, no encryption: the fastest result in the same measurement.

~0.4 s each

Many tiny commands. Every sgit command starts Python and derives its key; git starts in milliseconds. A loop of hundreds of commits wants the append lane, or the pack mode coming next.

1 commit / write

A write per request at high rate. One commit per change is right for documents; a stream belongs in a lane and is folded later.

blame, bisect

Tools sgit does not have yet. Path history and signatures exist; blame is a fold nobody has written.

sgit wins where the job can be selective, the files are large, or the storage is dumb; git wins on raw local speed for small, frequent commands.cli.sgit.ai · 21 October 2026 · from the newsroom's measured articles and this site's
