The same vault, today and in pack mode: the files on the host, and what each operation does

The comms vault, 35,423 objects on 14 October. Only the immutable part changes shape: loose objects one file each, or the same objects in zips. The mutable part, a handful of small files, is the same in both modes and moves the same way. Pack mode is proposed, not built.

immimmutable, named by its hash, written once   muwmutable, many writers, compare-and-swap   snwmutable, one writer, its owner overwrites it

Today: loose objects

bare/ data/ obj-cas-imm-… × 35,423, one file each keys/ key-rnd-imm-… public keys refs/ ref-pid-muw-… the named branch's head ref-pid-snw-… each clone branch's head indexes/ idx-pid-muw-… the branch index cache/ value, pointer derived, never authoritative

Push of a commit with 500 new objects

  1. batch write, 50 objects a request: 10 requests
  2. compare-and-swap the muw ref

Pull, 50 pushes behind

  1. read the ref; walk new commits, one request each
  2. batch read the trees and blobs it lacks
  3. merge, then the ref

Cold clone

  1. list the store (21 s), then about 700 batch reads
  2. 3½ minutes from the sandbox

Pack mode

bare/ packs/commits/ <epoch>__<commit>__<bytes>.zip one per push packs/snapshots/ <epoch>__<commit>__<bytes>.zip all objects packs/archive/ <epoch>__<commit>__<bytes>.zip absorbed keys/ key-rnd-imm-… unchanged refs/ ref-pid-muw-… ref-pid-snw-… unchanged indexes/ idx-pid-muw-… + features: [packs] cache/ value, pointer unchanged

Push of a commit with 500 new objects

  1. build one zip of them: 1 upload, straight to S3 if over 4 MB
  2. compare-and-swap the muw ref, as today

Pull, 50 pushes behind

  1. list packs/commits/: one request
  2. fetch the 50 packs it lacks, batched; verify every member
  3. merge, then the ref, as today

Cold clone

  1. newest snapshot (430 MB) and the packs since it
  2. about 40 s from the sandbox, expected
