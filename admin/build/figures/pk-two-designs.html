Two designs from the same evening, and what each asks of the server

How a push would work in each. Red boxes need something the server does not do today; teal boxes use what it does. The brief to the SG/Send team was written for the design on the left; the spec 48 minutes later chose the one on the right, which needs nothing new, and kept the append route for later.

Grow a zip in place

the brief · 20 Oct, 23:17 · one to three zips per vault
1

New route: presigned append, the server copies the zip's prefix inside S3 by UploadPartCopy

2

Upload the new members and a rewritten central directory, a few MB on a large vault

3

New parameter: complete with If-Match on the zip's ETag; a second writer fails and copies again

4

Then the ref, by compare-and-swap, as today

Gains: a pull is one Range read of the new tail; no compaction. Costs: a server change, and every writer contends on one object.

A new pack per push

the spec · 21 Oct, 00:05 · commits/, snapshots/, archive/
1

Build one zip of the commit's new objects, deterministic, named by its commit id

2

Upload it: batch write under 4 MB, presigned multipart straight to S3 above; both routes exist

3

Then the ref, by compare-and-swap, as today; packs never collide

Gains: no server change; contention only on the ref, as in every vault. Costs: a listing on pull, and compaction to keep the listing short.
