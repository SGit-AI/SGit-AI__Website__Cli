Where a vault key exists in clear: today, and with native PKI in sgit

An agent in a Linux container receives a vault key from another agent, with a person carrying the QR code between them. Today the key is sealed only while it travels. With native PKI it stays sealed at rest, and is opened only in memory, for as long as a command needs it.

Today: sealed in transit, clear at rest

1

The sender seals the key to the receiving agent's public key: a QR code. sealed

2

pki-agent open qr.png --save DIR writes vault-key-<id>.txt. a file on disk

3

sgit clone <vault key>: the key is an argument. shell history, the process list, the agent's transcript

4

The clone keeps it in .sg_vault/local/vault_key, and its signing key beside it. read by every later command

5

Anything that can read the folder can read every vault the agent holds: a backup, a zip, a leaked container image, another process.

Proposed: sealed in transit and at rest, clear only in memory

0

sgit id init: sgit makes the agent's key pair. A session key lives only in memory; a lasting key is locked by a passphrase or held in hardware.

1

The agent shows its public key as a QR code. The sender seals the vault key to it. sealed

2

sgit clone --sealed qr.png: opened in memory and never printed, never an argument, never a file.

3

The clone keeps .sg_vault/local/vault_key.sealed, sealed to the agent's own key.

4

Each command asks sgit agent, which holds the unlocked private key, to open it: about 2 ms. The key and what it derives stay in memory.

Clear on disk today: the vault key twice (a saved file and the clone), the clone's signing key, and the key on a command line.
Clear on disk proposed: nothing. A copied folder holds ciphertext addressed to a key that is not in it.
Still true either way: a process that can read the agent's memory while it runs can read the key. PKI shrinks where a key lives; it cannot make a running process unreadable.
