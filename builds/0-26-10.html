What changed

Signing with your own key

$ sgit commit -S -m "msg"                  # or -S<key>; --no-gpg-sign wins
$ sgit write -S notes.md …                 # a signed single-file commit
$ sgit vault tag create v1 -s              # or -u KEY
$ git config --global sgit.gpgSign true    # sign by default
$ sgit history log --show-signature
  • Off by default. Switch on with sgit.gpgSign = true. Git's own commit.gpgSign is deliberately not read, so a Git setup does not start signing vault commits.
  • Key and format from your global Git config: user.signingKey, gpg.format (ssh or openpgp; x509 is refused), gpg.ssh.program, gpg.program.
  • Who signs: an unencrypted ed25519 key in the process; everything else through ssh-keygen -Y sign or gpg.
  • Also signed when on: merge commits made by pull and branch merge, history revert --as-commit, vault ignore --apply.
  • A signing failure stops the commit and says how to commit without a signature.

The line differ is Git's (BR-2, BR-3)

  • Vault__Line_Diff is now a port of Git's xdiff (the pre-pass that sets lines aside, xdl_split and its cost heuristics), and compact gains Git's indent heuristic where Git uses it.
  • What changes for users: a few merges that used to be clean now stop with markers, exactly where git merge-file stops. The patch text of some diffs, the boundaries of some commit -p hunks and blame on repeated lines move to Git's placement.

Compatibility

  • No gate, no new minimum client, no format change for a vault that nobody signs in. An unsigned commit is stored as before.
  • Old clients and CLI-signed commits: a vault with four commits signed by the CLI (SSH and OpenPGP) among six others was cloned by 0.20.0, 0.24.0, 0.26.0, 0.26.6 and 0.26.11. Each: fsck ok, 10 of 10 clone signatures verified, a commit on top, a push.
  • Old vaults made by 0.20.0, 0.24.0 and 0.26.0 (normal and pack) open in 0.26.11, take a commit and a push, and the old client pulls it back.
  • The web UI (W-1): the CLI team states that the web UI never verifies commit signatures and ignores members it does not know. I could not test it. If that holds, W-1 is answered; ask the web UI team to confirm with one signed vault before 0.27.0.

BR-8 (low): a failed signing says "nothing was written", but two objects were

  • On each failed commit -S, the blob and the tree are already written; the commit object and the ref are not. The object count rose by 2 per failure (3 on a success), five failures in a row left ten unreferenced objects.
  • They are harmless (fsck is clean) but the message is not exact. Either say "no commit was made", or sign before storing the tree. The error also repeats its prefix: gpg: gpg: signing failed: No secret key.

Also noted

  • Not tested: passphrase-protected keys, ssh-keygen as the signer (not installed on the test machine), certificates and FIDO keys, merge and revert signing, vault tag create -s.
  • sgit check fsck ignores --vault PATH and looks in the current folder (0.26.8 too).
