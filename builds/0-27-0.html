The CLI team's rule for 0.27.0: nothing high or medium open, the checks for every claim since 0.26.0 hold on the candidate, and the cross-version checks pass. All three hold. Everything below was run on 0.26.12.dev0, or on 0.26.11 with the code diff to the candidate read (two files, a comment and the version).

Do these first

  1. Yank 0.26.3 to 0.26.11 on PyPI, and check it. None was yanked when I checked. Today a plain pip install sgit-ai and sgit update on a release install both give 0.26.11, a dev build. After the yank both give 0.26.0 until 0.27.0 is published.
  2. Decide R3-1 and UP-1 (below): fix, or write them into the release notes.
  3. Ask the web UI team to open one vault that holds signed commits and tags. The CLI team says the web UI never verifies commit signatures and ignores members it does not know; signing shipped on that. I could not test the web UI. A signed vault from the scripts here takes minutes to make.

For the release notes of 0.27.0

New: history blame, sgit grep, log -S/-G, rename detection and --follow, commit by path and by hunk, push with uncommitted changes, opt-in line-level merge, 64 KB messages, commit -S and user signatures with check verify, check upload-history, faster pack index verify.

Fixed: a push of more than 100 commits left a gap on the host (every build since at least 0.26.0); a merge on a fork deeper than 200 commits; commit during an unresolved merge; nested vaults; and the line differ.

Changes that can break a script:

  • commit -m "msg" y: y is now a path.
  • history log/show/diff --json: a renamed file is in files_renamed, no longer in files_added and files_deleted.
  • The patch text of history show/diff is git diff's; rename detection is on by default.
  • sgit grep patterns read like git grep -E.
  • sgit.gpgSign, not Git's commit.gpgSign, turns signing on.
  • Dev builds are X.Y.Z.devN pre-releases; a plain install gets the release.
