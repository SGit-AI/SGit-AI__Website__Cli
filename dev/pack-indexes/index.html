Pack indexes for sgit: a design pack

Shipped, 27 October 2026. Phases 1 to 3 of this pack, with a selective working copy the CLI team added, shipped in sgit-ai 0.26.0: the release notes, and the story, the reviews and the measurements. Phase 4, reading a file with no clone, is not built. The text below is the design as written.

Status: design, 26 October 2026, for the sgit CLI team. Nothing here was built when it was written. It is written against SGit-AI__CLI at c0694753 (branch claude/charming-babbage-5hzcxq, after 0.25.0) and the code names below are from that commit.

Compatibility is a requirement.

  • A vault with index packs works unchanged for every client from 0.24.0 to 0.25.0. They never list the folder the index packs live in.
  • No min_client rises.
  • A vault without index packs works unchanged for new clients, which fall back to today's walks.

Audience: the agents and engineers who will build this. Read in order.

1. The problem

0.25.0 made local commands follow the size of the change. What still follows the size of the vault, on a pack vault, is everything a reader has to recompute or download that the writer already knew:

Cost todayMeasuredWhy
A clone writes every object loose before anyone can work305,230 object writes on the CLI team's 228,000-file vault (clone 216 s); 11.6 s for 134,092 objects on a fast disk here; on a cloud session's disk the curator's first command waited 17 minutesextract_pack unpacks every member into bare/data/
A partial clone of a pack vault is not partial on the wirethe newsroom's 1.22 GB snapshot to read one folderStep__Clone__Bulk_Fetch.pack_vault_fetch: "a partial clone (--path/--depth) still takes the packs whole"
A pull's commit list and merge base walk historyabout 0.4 ms per commit of history (1.9 s on 5,000); the branch bounds it by a day of clock skewno generation numbers anywhere
history log diffs trees7.4 s for 10 commits on the 228,000-file vaulteach commit's change is recomputed by walking where tree ids differ
A pull of a pass checks every blob for presence6 s of the 31.7 s pull on the branch (exists over 235,000 ids)no list of what the new commits added
The first flatten of a head this clone has never seenabout 45 s full; the branch copies unchanged folders and reads changed treesthe writer had the map and did not send it

What is not in scope: the stat pass of status (4 s at 76,000 files, 15 s at 228,000), writing the working files a working clone needs, and the bandwidth of a full clone. Indexes do not remove those.

The largest gains are for readers that want part of a vault (gigabytes become megabytes), for history questions (seconds become milliseconds), and for clones on slow disks (Phase 3). For a working clone that touches every file, the working copy itself remains the cost.

3. The principles

Dinis Cruz's, tested in Indexes the writer pays for:

  1. The writer pays. The client that pushes computes the indexes once. It already holds the answers: its flat cache, the changed paths, the parents.
  2. Cross-reference in both directions, so a reader goes from any id to everything that points to it.
  3. One index per question, sharded the way that question walks: commits by generation, folders by path, blobs by id.
  4. Plain JSON, typed at the writer. The writer builds through Type_Safe schemas; the reader loads JSON as dicts. No database file travels.
  5. Load on demand from the zip, one member at a time, located by an offset table the writer stores.
  6. One file per folder, rewritten on the paths a commit changes, as trees already are.

And one rule from the CLI team's architecture, kept unchanged: an index is a plan, never a proof. Every object is verified by its content address before it is used. Lose every index and nothing is lost.

TermMeaning

5. Decisions

#DecisionWhyChanges from the CLI architecture
D1Index packs live in bare/packs/indexes/{commits,snapshots,archive}/, never inside a data pack0.24.0 to 0.25.0 refuse an unknown member in a data pack and re-download that pack on every pull (tested on 0.25.0 from PyPI). They list only bare/packs/commits/ and bare/packs/snapshots/, so they never see index packsyes: the architecture put bare/index/* members in the data pack and gated it
D2No min_client change. An advisory feature pack-indexes in the branch index says "writers here produce index packs"unknown features are ignored by 0.24.0 to 0.25.0 (Vault__Format.gate_this_build_carries, check_client) while min_client staysyes: no gate
D3Members are JSON, deflated, then encrypted with the read key (Vault__Crypto.encrypt), one AES-GCM envelope eachJSON-native; same primitive as trees; no database file to trustno
D4Member names in the zip are opaque sequence numbers; their meaning is only in the encrypted headerthe host learns nothing from names: not paths, not which object is a tree, not which folder changedrefines: no keyed names needed
D5The header is signed by the pusher's clone key over its canonical JSON, which lists every member's plaintext SHA-256the index gets exactly the standing of the commit it describessame intent
D6A snapshot index carries flat, folder:*, commits:*, commit-gen, blob-paths:*, file-commits:*; a commit index carries changes and the folder:* members on the changed pathsthe snapshot answers every question; a delta costs 3.1 KB for a five-file commit, against 47.7 KB when shards travelrefines flat/, diff/, graph/
D7Generation numbers live in index members, not in commitscommit_v1 has no field for it, and a commit-schema change would be a gateyes: the architecture proposed them in graph/ members, same idea
D8New data packs store members in path order: commits, then trees by path, then blobs by the path of their first useone folder becomes one contiguous range; the order is a function of the tree, so packs stay deterministic; pack verify and old readers ignore ordernew
D9folder:* members carry each blob's at: data pack, offset, lengtha scoped reader never parses a data pack's central directory (10.7 MB for 134,092 members)new
D10Missing or bad indexes fall back to today's walks, per packmixed writers (0.25.0 pushing to an indexed vault) leave gaps; a reader must never depend on an index existingsame
D11Readers keep index packs encrypted on disk and decrypt members on readnothing new in clear on disk, compatible with sealed vault keys; decryption is about a microsecond per KByes: the architecture assembled into SQLite on disk
D12No SQLite, no graph engine, no new dependency. Dicts and the standard librarymeasured: dictionaries answered every question fastest; databases added load timeyes: SQLite was the architecture's local form

6. Phases

PhaseWhatRemovesSize
1Index packs: writer at push, compaction, pack import; sgit pack index build/verify/stats; reader for pull (commit list, merge base, missing blobs, new flat map), history log, first flatten after clonethe history walks and the per-blob presence check; the first full flatten4 to 5 days with tests
2Path-ordered data packs with at offsets; clone --path and scoped pull on pack vaults by ranged readsthe whole-pack download for partial clones3 days
3The pack as the store: keep packs, read in place, verify on first read (the CLI architecture's phase 1)the 305,230 object writes of a clone3 days
4Readers without a clone: sgit cat/fetch of a path from the index packs and one ranged readthe clone itself, for readerswith the SG/Vault team

Phase 1 is independent of 2 and 3, and has the widest effect. Phase 3 is local only and can run in parallel. Each phase ends with its acceptance tests (04) green and its benchmark run on the 76,000-file vault and the 228,000-file synthetic vault.
