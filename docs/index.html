sgit and Git: what only sgit does, what both do, and where Git is ahead

The row-by-row comparison, checked against sgit-ai 0.26.0 and the dev builds after it. Twelve things Git has no equivalent for, each with the command and Git's nearest answer: a host that reads nothing, read keys that work from any static host, custody without access, writes without reads, one folder by byte ranges from plain storage, indexes the writer ships encrypted and signed, policy the vault carries, rewinds refused by name, a secret guard, key rotation, a computable cache, files sealed to a person. Fifteen things both have, with what differs. Where Git is ahead: line-level merge and partial commits shipped in the dev builds of 28 October; the rest of the CLI team's Git-parity roadmap is designed, with sizes in days. GitHub's features move to a future server. And the six things zero knowledge rules out, each with its substitute.

sgit clone --path holds one folder and carries the rest by id; --depth holds the newest commits only. Measured on a 600-commit vault: one folder in 14 s against 80 s for the whole vault. The rules, widening with sgit fetch, the commands that need a full clone, and the two edges.

sgit-ai 0.25.0 release notes: large vaults

Release notes for sgit-ai 0.25.0, for people and agents. On a large vault, the cost of a command now follows the change, not the vault. On a vault of 76,000 files a one-file commit went from 29 minutes to under 5 seconds and a status from 71 seconds to about 4. What changed (trees read as JSON, the flattened head cached, a linear and incremental tree builder, a scan cache keyed like git's index, no tree walk when a push's server has nothing new, history log by tree diff), the data-loss bug a review found in the first version of the scan cache and how it was closed, the two new cache files and what they hold, and what is still slow. Nothing changes on the server or in a vault's format.

Using sgit from Claude on a Team or Enterprise plan: the network allowlist

On Claude Team and Enterprise plans an Owner sets the code sandbox's network access for the whole organisation, and the default blocks every sgit host. Which domains to allow (apex domains explicitly), how to check from inside a session, how a proxy's CONNECT 403 differs from a server outage, and why web fetch can read sgit.ai while the shell cannot.

sgit-ai 0.24.0 release notes: pack mode

Release notes for sgit-ai 0.24.0, for people and agents. Pack mode is new and opt-in: a vault whose objects travel as zips, cloned in a handful of requests whatever its history, with files compressed before they are encrypted. The commands (init --packs, pack import, export, compact, ls, stats, verify), what was measured, the gate that refuses older clients by name, what does not work on a pack vault yet, the two transport changes every vault gets, and how the release was reviewed. Normal vaults behave as before.

sgit-ai 0.26.0 release notes: pack indexes, selective working copies, the pack store

Release notes for sgit-ai 0.26.0, for people and agents. Every push to a pack vault now writes an index pack beside its data pack, so readers stop walking trees. A pull plans its fetch from the indexes, and history log reads change lists. A clone can skip writing the working copy, and an agent then checks out only the files it needs. A clone can keep the packs in place instead of unpacking hundreds of thousands of objects. A clone of one folder takes that folder by byte ranges. On a 76,000-file vault, a full clone fell from about two minutes to one, a no-checkout clone takes about 28 seconds, a one-folder clone under 3 seconds against 36, and history log half a second against three. The new agent loop, the commands, the compatibility rules (a pack vault created by 0.26.0 needs 0.26.0), what is on disk, and what is still slow. Nothing changes on the server.

sgit-ai 0.26.10: sign commits and tags with your own key; the line differ is Git's

Dev build of 28 October 2026, from the CLI's dev at bbc51d9f. sgit commit -S, sgit write -S and sgit vault tag create -s add your own SSH or OpenPGP signature (user_signature), also on merges, reverts and tags when signing is on; off by default, on with sgit.gpgSign. sgit-ai 0.26.9: a push of any size uploads every commit (BR-1 fixed)

Dev build of 28 October 2026, from the CLI's dev at 9345a1fc. Fixes BR-1, the high finding in every build since at least 0.26.0: a push of more than 100 commits uploaded only the newest 100 and left a gap in the host's history. sgit-ai 0.26.8: history, blame and search; renames found as Git finds them

Dev build of 28 October 2026, from the CLI's dev at bc904c1b, and what a plain pip install gives today. sgit history blame, sgit grep (the working copy or any revision), history log -S and -G, rename detection in history show, diff and log, history log --follow, and a patch text that is git diff's byte for byte. Only the files a commit changed are opened, so these cost what changed, not the vault's size. sgit-ai 0.26.7: verify the signer's own SSH or OpenPGP signature on commits and tags

Dev build of 28 October 2026, from the CLI's dev at 0d486aaf. A commit or tag can carry its signer's own SSH or OpenPGP signature (user_signature, Git's gpgsig) beside the per-clone signature every commit already has, and this build checks them, with Git's verdicts and Git's trust files. sgit check verify, history log --show-signature, history show --show-signature and vault tag show report them. sgit-ai 0.26.6: commit some paths, commit some hunks, push with uncommitted changes

Dev build of 28 October 2026, from the CLI's dev at 036e33b5, and what a plain pip install gives today. sgit commit takes paths, as git commit -- paths does, and leaves every other change on disk. sgit commit -p picks hunks interactively; agents use --list-hunks and --hunk ID, with ids that refuse to pick a different hunk once the file has changed. sgit push no longer refuses uncommitted changes. One behaviour change for scripts: with -m, extra words are now paths. sgit-ai 0.26.5: line-level merge, opt-in

Dev build of 28 October 2026, from the CLI's dev at 43e1889c. sgit pull --merge lines and sgit branch merge --merge lines merge a file both sides changed line by line, as Git does, with Git's conflict markers in the file and --conflict diff3 for the base too. The default does not change: whole-file .conflict copies. Reviewed by cli.build. 5,030 tests pass and the four end-to-end checks hold. In 18,000 random merges against git merge-file, all 8,925 with unique lines were byte-identical. Where lines repeat, 2 of 4,544 code-like merges came out clean where Git reports a conflict (BR-2), and 0.9% placed conflict blocks differently (BR-3). Maturity good for an opt-in feature: review line-merged files before pushing.

sgit-ai 0.26.4: commit messages up to 64 KB

Dev build of 28 October 2026, from the CLI's dev at c495b40e. A commit message longer than 740 bytes used to fail with a raw ValueError, after the commit's blobs and trees were written; Git has no limit. The default limit stays 740 bytes, now refused before anything is written. A vault with the long-messages feature takes up to 64 KiB, and every client reads messages up to 1 MiB, the web UI's. Turning the feature on raises the vault's gate to 0.26.4, so an older sgit is told to update. Reviewed by cli.build. All checks held, including the refusal of 0.26.0 and 0.26.3 clients with a clear message. Maturity good. Wait for the 0.27.0 release before turning long-messages on in a vault that agents on 0.26.0 still use.

sgit-ai 0.26.3: Git-parity phase 0, merges made safe, and dev builds on PyPI

Dev build of 28 October 2026, from the CLI's dev at 16c46e89, and the first published as a plain version. It fixes the bugs the seven Git-parity designs found. sgit commit during an unresolved merge put the .conflict files into the vault; it now refuses. status shows a merge in progress. Identical content on both sides is no longer a conflict. Merges and pushes on forks deeper than 200 commits work. A nested vault is never committed. Object files are written atomically. Merges, writes and sparse commits rebuild only the changed folders. From this build, every dev merge is published as X.Y.N, and a plain pip install takes the newest. Reviewed by cli.build. 4,921 tests pass and every fix held, including a 250-commit fork that 0.26.1 merged against an empty base. Maturity good. One decision for Dinis Cruz: plain installs now get dev builds (BR-4).
