sgit and Git

sgit is not a copy of Git with encryption on top. It has Git's verbs, so a Git user is at home in an hour. But the host reads nothing, and that makes possible a set of things Git cannot do at all. This page is the map, row by row, checked against sgit-ai 0.26.0:

  • what only sgit does;
  • what both do, and how they differ;
  • where Git is ahead, and how fast the gap is closing;
  • what zero knowledge rules out for good.

In one paragraph. Use sgit when the files must stay unreadable to whoever stores them, when readers should need no account, or when many agents work in one large vault, one folder each. Use Git when you need blame, bisect or rebase today, a forge's review and CI, or twenty years of tooling; line-level merges and partial commits arrived in sgit's dev builds on 28 October. Almost everything on Git's side runs on the client in Git too, so sgit can build it. What sgit can never do is anything that needs the host to read your files.

The evidence:

  • the sgit CLI team's claim-by-claim review of the newsroom's article What sgit does that Git does not, against the CLI's source and threat model;
  • three behaviours re-run by this site against the PyPI release, the script;
  • Git's and GitHub's own documentation.

1. What only sgit does

"No equivalent" means the mainstream Git toolchain and GitHub. Add-ons such as git-crypt and git-remote-gcrypt cover parts of the first row, with the trade-offs their own READMEs state.

#What sgit doesHowGit's nearest answer
1The host reads nothing. Contents, file names, commit messages and branch names are encrypted on the client (AES-256-GCM) before they leave itevery command; objects stored under opaque idsgit-crypt encrypts contents only; its README says it "does not encrypt file names, commit messages" or other metadata
2A read key is a capability, not a permission. It is derived one way from the vault key, so it can never become write access. It reads from any static host, with no account and no server codeclone --read-key, --transport static, sgit publishread access is a role a server enforces (a collaborator, a deploy key), or the repository is public
3Custody without access. Copy a published vault you cannot read, keyless, and verify it. A backup service or a second host holds and checks the vault and learns nothingsgit vault mirror [--verify DIR]a mirror of a Git repository can read all of it
4Write without read. An append lane lets a sender put something into a vault and learn nothing, not even whether anyone else writes there: the answer is {"ok": true}the server's append lanes; no sgit command yetno Git or GitHub role can write without reading
5One folder by byte ranges from plain storage. A scoped clone of a pack vault reads the packs' directories, then only that folder's byte ranges, verifying each object by its hash. On 76,000 files: 2.8 s and 12.5 MB, against 36 s and the whole 88 MB packclone --path on a pack vault (0.26.0)Git's dumb HTTP takes whole packs; its partial clone needs a smart server that reads the content
6Indexes the writer ships, encrypted and signed. Each push carries an index pack beside its data pack, so readers plan pulls and clones without walking trees. An index is a plan, never a proof: every object is still verified by its idautomatic on pack vaults (0.26.0); pack index build | verify | statsGit's commit-graph and pack indexes are built by each reader, as local plaintext caches
7Policy carried by the vault. The format gate (min_client, features) and signatures-required live in the encrypted branch index. Every sgit client enforces them before it writes anythingsgit vault format (0.19.0)signature checks are each user's local config; a repository cannot require them of whoever clones it
8A rewind is refused by name, on every clone. A remote head that does not descend from the last one this clone accepted is refused, even though the host took the forced push (it cannot read refs)pull refuses; pull --accept-rewind takes it (0.19.0)the default + refspec takes a forced update with one line of output; receive.denyNonFastForwards is a server setting
9A secret guard at commit. A vault key in a zip under any name, a hard link to one of the clone's secrets, and .env files are refusedcommit, writenothing built in; GitHub's push protection runs on a server that reads the content
10Rotate the key that encrypts the history. Move a vault to a new key, and optionally a new serversgit vault rekey, vault movea leaked credential is revoked on the server; the content was never encrypted
11A computable cache. A hot path gets a fixed-cost read at a location only key holders can compute, so an edge function reads it in one request, without walking treessgit cache addevery read walks from a ref
12Seal a file to a person. Encrypt a file to someone's public key, then commit the sealed filesgit pki encrypt --recipientGit signs commits; it has no "encrypt this to that person"

3. Where Git is ahead, and how fast the gap is closing

Git is a client-side program. Almost all of its lead runs on the client in Git too, on plaintext the client holds, so sgit can build the same things with no new server feature.

  • The plan: the CLI team's Git-parity roadmap (28 October): Git the client is the bar, and every new feature is off by default.
  • The first deliveries are already on PyPI as dev builds, each reviewed.
  • Sizes are the roadmap's estimates.

Moved to a future server, "SGitHub" (the roadmap, section 4): GitHub's features, not Git's.

  • accounts, and who pushed;
  • branches protected per person;
  • an owner-signed list of who may write, which closes TM-R01;
  • review, CI and verified badges.

These are possible under zero knowledge, with per-member write tokens checked by ref id and review objects kept in the vault, but they belong to a host, not to the CLI.

4. What zero knowledge rules out

These are limits of the model, not of effort. Each has a substitute on the client.

Ruled outWhyThe substitute
anything the host must read to do: server-side search, diffs, a merge button, code scanning, language statisticsthe host holds ciphertext; giving it the key ends zero knowledgedo it in the client, the browser, or a runner the key holder controls
taking back what a reader already hasno system can; a removed GitHub collaborator keeps their clone toorotate forward (vault rekey, vault move), delete the old vault; per-folder keys limit what each reader ever got
per-folder permissions inside one keythe host cannot tell folders apart, and the key decrypts every objectper-folder keys (section 3)
hiding all metadatasizes, timing, counts and access patterns are visible to any storepadding, fixed-size packs and decoy reads reduce it at a bandwidth cost; only an ORAM-style protocol removes it
the host optimising the store: repacking, deltas, dedupe across vaultsthe host has only ciphertext; dedupe across vaults would need convergent encryption, which leaks equalityclient-side deltas and prune (section 3)
a host that enforces fast-forward-onlythe host cannot read a ref, so it cannot check ancestrythe client-side rewind guard (row 8), shipped

5. The qualifiers

Said plainly, so that nobody builds on a stronger claim than the code makes:

  • What the host still sees:
  • sizes, timing and object counts;
  • in pack mode, which commit each push carried;
  • which trees are equal, because tree encryption is deterministic;
  • with blob-deflate, how compressible each file is;
  • the sizes of index packs;
  • in path-ordered packs, which blobs share a folder;
  • for a scoped clone, which byte ranges it read.
  • Reading is a capability; writing is a permission. The write key is a bearer secret that the host checks, with no cryptographic role. A read-key holder who can write to the store can author history that check verify calls verified. A signature today proves "a key holder", not a particular clone or person. This is the threat model's top accepted risk, TM-R01. On the roadmap, own-key signing (design 02) lets each verifier decide whom to trust, as Git does, and an owner-signed list of who may write moves to the future server.
  • An index is checked under the vault's signature policy. An unsigned index is accepted unless the vault has signatures-required. A signing teammate could mislead a fresh clone's working copy, as a commit from that key could. sgit pack index verify catches it (TM-R42).
  • A read key cannot be revoked after the fact, and it is per vault, not per folder (TM-R12). The remedy is rotation, as above.
