# The sgit CLI: git for encrypted vaults, documented from the code

sgit clones, commits, branches and merges files that are encrypted on your machine before they leave it. The server stores ciphertext under opaque ids and never sees a filename, a file's contents or a commit message. This site is the CLI's documentation: what each command does, the HTTP API underneath it, the guides for people and for agents, and the research behind the design.

```text
$ pip install sgit-ai          # Python 3.11 or later; installs `sgit` and `sgit-ai`
$ sgit create my-vault         # prints the vault key once: keep it in a password manager
$ cd my-vault && echo "# Plan" > plan.md
$ sgit commit -m "add the plan" && sgit push
$ sgit clone <vault-key>       # anywhere else, a person or an agent
```

**Where things are.** The project, the vault platform and what is built on top of it are on [sgit.ai](https://sgit.ai). Everything about the command-line tool is here.

- [A vault in one file: native zip support for sgit, where it wins, where it loses, and what already exists](articles/a-vault-in-one-file.md): A vault is files and folders, so it can be a zip. Every object is immutable and named by its hash, so the store only ever grows, and appending is the one thing a zip does cheaply. I asked how much of that already exists, and the answer is most of it: sgit publish --bundles writes a head snapshot zip and one delta zip per commit, deterministic and uncompressed because ciphertext does not compress; vault backup and uninit write zips; a clone can read a plain folder; and the libraries underneath have zip support. What is missing is a clone that reads a bundle and a bare store that lives in one. The cost today is requests, not bytes. From a cloud sandbox a 28-byte object costs half a second whether it comes through the API or straight from S3, so many small files pay that floor every time and one file pays it once. On the article's 12 MB vault, 106 separate requests took 2 to 2.5 seconds and one 12.7 MB zip took 0.05 seconds to fetch and 0.08 to unpack. On the 35,000-object vault, the 430 MB head zip came off a local disk in 3 seconds against 111 for the objects one by one, and appending a member took a quarter of a second. Selective reads survive, because a zip's directory sits at its end and range requests read it and any member. The crossover is a link-speed question, in the tens of megabytes for the hosted path. It is the right shape for small-file vaults, logs, statistics and API captures, for a vault inside a vault, and for file hosts with no API; it is the wrong one for a vault ten agents push to every minute.
- [Streaming changes into a vault: a thousand small writes, one commit, every line attributed](articles/streaming-changes-into-a-vault.md): Every change in a vault is a commit, and a commit is a tree rebuild, a signature and a compare-and-swap on one ref. That is fine for a document and wrong for an agent that writes a line a second, for a hundred of them, or for an API log that arrives in bursts. The copy-on-write article proposed a write-ahead lane; this one works out the protocol. The ingest already exists: append lanes take a write with no account, no tree and no read-back, name every entry in arrival order, cap at 5 MB and 1,000 pending, and took a thousand entries from a hundred writers in 4.9 seconds on the in-memory server. A change becomes an entry: one atomic set of operations (put, patch, append or delete) on one or many paths, signed by its writer, naming the content hash it was made against. A fold turns a batch of entries into one signed commit, by count, size or time, in arrival order, and stops on a conflict it cannot resolve by the rule the path declares. Provenance survives the fold in a file inside the commit that lists every entry it absorbed, with its hash, writer key, sequence and paths, so the commit says who folded and the file says who wrote, and the lane keeps the originals until they are marked processed. Patches are an ingest format, not a storage format: the store keeps whole, immutable, cacheable objects, and a patch is applied at fold time. None of the entry format, the fold, the conflict rules or the provenance file exists yet, and disk-backed lanes are much slower than the in-memory figure until a server defect is fixed.
- [sgit is a standard, not a server: everything in a vault is one hash away](articles/sgit-is-a-standard-one-hash-away.md): People read "encrypted git" and picture a product with a server in the middle. There is a server, and it is the least interesting part. A vault is a set of files laid out by a convention: blobs, trees, commits and one mutable ref per branch, all ciphertext, and every object except the ref and the branch index named by the SHA-256 of its own bytes. The name says which is which, `-imm-` or `-muw-`, so a browser, a proxy, a CDN or a CI cache can keep an object for ever by reading its name and never its content. Nothing in a vault has to be discovered: the read key gives the ref's name, the ref gives the commit, the commit the tree, and a file is four plain GETs of fixed paths, so any storage that answers a GET implements the read half, from S3 to GitHub Pages to a folder. Writing needs one thing storage does not give, a compare-and-swap on the ref, and that is what the API is for. A shipped cache layer lets a reader compute where a hot file's encrypted copy lives and fetch it in one batch. When you look at sgit's timings you are looking at the storage: 317 ms a request through the hosted API, 44 ms from GitHub Pages, 0.8 s for a scoped clone against a local server that takes 13 s hosted. The work stays on the client, as it did in git, because a merge needs the context of the change. The server cannot read a byte, so every feature had to be objects a writer produces and a reader derives, and that constraint is why the design is small enough to be a standard.
