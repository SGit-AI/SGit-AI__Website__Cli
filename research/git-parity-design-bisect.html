1. Summary, and the exact Git behaviour matched

sgit history bisect finds the commit that introduced a change by binary search over the commit graph, like git bisect. The user (or a command, with run) marks commits good or bad; sgit writes each candidate commit into the working copy until one commit is left.

The one structural difference from Git is where "HEAD" is. Git detaches HEAD and leaves the branch alone. sgit has no separate HEAD: the clone branch's ref is the head. So bisect never moves any ref. It records the commit under test in a local state file and writes that commit's files into the working copy; status, cat, ls and checkout read that commit while a bisect is in progress. reset writes the clone head's files back. Because no ref moves, a lost or damaged state file can never lose a commit: the head was never touched.

2. Scope and non-goals

In scope: start, bad/new, good/old, custom terms, skip (single revs and A..B ranges), next, reset, log, replay, view/visualize, run, terms, status (sgit extra: the state as text or JSON), --first-parent, --no-checkout, a pathspec, --json on every subcommand. Full, selective (sparse / no-checkout), scoped, shallow, read-only, pack and pack-store clones. The commands that must refuse or change behaviour while a bisect is in progress (7.1).

Not in scope:

  • gitk. view prints a log; nothing graphical.
  • Moving refs. Bisect never writes a ref, a baseline, the branch index or the reflog.
  • Network writes of any kind (6.3 proves it).
  • Fetching history behind a shallow boundary on its own. A shallow clone says so and stops (7.3).
  • Committing during a bisect. Git allows commits on its detached HEAD, which bisect reset then orphans; sgit refuses them (decision D1).
  • Changing branch checkout <commit>'s existing "detached" behaviour (CLI__Vault.py:1567, which writes every file of the commit with no state and no dirty check). It is a related hazard noted in 11 (D7), not fixed here.

5.3 The candidate set

Input: bad, goods (≥ 1), skipped, paths, first_parent.

  1. Painting walk (Vault__Bisect__Graph.candidates). A max-heap of (generation, commit_id) starts with bad (flag NEW) and every good (flag OLD). Pop the highest generation; merge flags if seen; push its parents (only the first with first_parent) carrying the flag. Stop when every entry left in the heap is OLD (the paint_down_to_common rule: nothing below can be NEW-only). Candidates = commits painted NEW and not OLD. Generations come from Vault__Pack_Index.generation_of (Vault__Pack_Index.py:137), memoised in local/index/generations.json. On a loose vault the memo is built on first use (one decrypt per commit, once per clone). A commit not in the store (a shallow boundary's parent) has generation 0 and no parents. Unbounded: no limit=200 (unlike find_lca, Vault__Fetch.py:78).
  2. Pathspec (when paths is non-empty, or by default on a scoped clone, 7.3). A candidate is kept when touches_paths is true:
  • for each path, resolve the entry id (tree id or blob id) at that path in the commit's root tree and in each parent's, walking only the spine (one tree read per path segment, Vault__Sub_Tree._entries_by_name, Vault__Sub_Tree.py:306);
  • a non-merge commit touches when any id differs from its parent's;
  • a merge touches when, for some path, its id differs from every parent's (the merge itself changed it). Commits not kept stay in the graph for reachability (weights count only kept commits reachable through them). This approximates Git's history simplification, which also prunes merge parents; it is equal to Git on linear histories (tested, 9.3) and documented as an approximation for merges (decision D4).
  1. Skipped commits stay candidates for counting (as in Git) and are excluded only when choosing.
  2. Ancestry check before the first step (merge_bases_ok false): for each good g, if is_ancestor(g, bad) is false (Vault__Ref_Guard.is_ancestor, :23), compute merge_bases(g, bad) (all of them, by painting).
  • A merge base not yet marked: it is the next commit to test, with the line Bisecting: a merge base must be tested.
  • A merge base marked bad: stop with Enum__Bisect_Status.MERGE_BASE_BAD and Git's message, plus a hint: if you are looking for the commit that FIXED something: sgit history bisect start --term-old broken --term-new fixed.
  • A merge base marked skipped: print Git's warning (… we cannot be sure the first bad commit is between <mb> and <bad>. We continue anyway.) and continue.
  • All good: set merge_bases_ok = True, then continue normally.

5.4 The midpoint

n = len(candidates). For each candidate c, w(c) = number of candidates reachable from c through the graph (c included). Computation: process candidates in increasing generation; reach(c) = {c} ∪ ⋃ reach(p) over parents restricted to the candidate subgraph. A bitset per commit (Python int used as a bitset, candidates indexed 0..n−1) keeps this exact for DAGs at n · n / 8 bytes: 10,000 candidates is 12.5 MB, acceptable. For n > 50,000, use Git's approach: exact counts for single-parent chains (w = w(parent) + 1) and a bitset only below merges. Linear histories are always O(n).

Choice (best):

  • score(c) = min(w(c), n − w(c));
  • skip commits in skipped;
  • choose the highest score; ties go to the smaller w, then the lower generation, then the smaller id.

That tie rule reproduces Git on every vector run here (9.3): 15 linear → c8 (w = 7, not c9 with w = 8); first-parent 5 → m3; the merge graph → b3. Git's own tie order depends on its counting order and, under skip, on SHA-1 order, so for DAGs with ties the tests assert this documented rule, not Git's pick.

Progress numbers: remaining = n − w(chosen) − 1, steps = estimate_steps(n); for 15 → 7, 3.

Termination:

  • n == 1 (only bad left): first_bad = bad, status FOUND.
  • Every candidate but bad is skipped: status ONLY_SKIPPED, possible = skipped candidates plus bad, sorted by generation descending (Git prints them that way).
  • Shallow clone and first_bad is a boundary commit (Vault__Scope.is_boundary): print <id> is the first bad commit this clone can see: its parents are behind the shallow boundary (sgit fetch --unshallow, then sgit history bisect replay <log>); status FOUND, "at_boundary": true in JSON.

5.5 Skip (skip_away, ported from Git)

When the best candidate is skipped:

  1. Sort the non-skipped candidates by score descending, ties by w ascending, then id (Git sorts by distance then oid).
  2. count = len(sorted), prn = ((count * 1103515245 + 12345) & 0xFFFFFFFF) // 65536 % 32768, index = (count * prn // 32768) * isqrt(prn) // isqrt(32768).
  3. Choose sorted[index]; if that is bad, choose the entry before it, or sorted[0].

Vectors (count → index): 14 → 0, 13 → 6, 12 → 0, 7 → 3, 6 → 0 (computed with this formula; with Git on the 16-commit history, skipping c8 gave c9 (index 0) (run)).

skip A..B marks every commit in ancestors(B) − ancestors(A), as Git does.

5.6 Moving the working copy between steps

Vault__Bisect__Working_Copy.move(directory, from_id, to_id, state):

  1. Diff. diff_trees(tree(to), tree(from)) (Vault__Sub_Tree.py:259): only differing folders are opened. On a scoped clone, flatten both with Vault__Scoped_Tree.flatten (in-scope only) and diff the two maps. Result: writes (added and modified in to), deletes (in from, not in to).
  2. Guard (before any write). The pull guard, with "ours" = flat(from) and "merged" = flat(to):
  • scan = _scan_local_directory(directory, verify=touched);
  • dirty = Vault__Pull__Guard().dirty_paths(directory, ours, scan, obj_store=…, sparse=…, checkout=…);
  • plan = guard.plan(dirty, ours, merged, scan, blob_hash_fn=…);
  • blocked = plan['blocked'] + guard.blocked_targets(directory, writes, deletes).
  • A blocked path refuses the step with Vault__Dirty_Working_Tree_Error(guard.message(blocked)), nothing written: Git's "Your local changes to the following files would be overwritten by checkout".
  • Dirty files the move does not touch are carried over (Git behaves the same). Flattening from and to in full is avoided: the guard only needs the entries for touched paths, which the diff already returned, plus scan.
  1. Selective clones. Pull__Selective().setup(directory, obj_store, local_config, no_checkout=False); to_write, skipped = selective.split(writes). Paths not checked out stay not checked out and are reported as not_written. After writing, selective.after_write(written, deletes, stale=selective.stale_of(skipped, ours)) keeps the checkout record right (Pull__Selective.py:59).
  2. Missing blobs (a loose sparse clone): batch-read through api.batch_read, verified before they are saved, exactly as Vault__Sync__Checkout._download (Vault__Sync__Checkout.py:160). This is a read; see 6.3.
  3. Write. _remove_deleted_flat for deletes, then _checkout_flat_map(directory, to_write, …, failed=failed) (Vault__Sync__Base.py:674), which also seeds the scan cache. Any failed entry raises after the state records current = to_id (the files that were written are to's), with the paths and reasons; status shows them as modified, and next or reset retries.

5.6.1 Write order and crash recovery

  1. Write the state with transition = {from, to}.
  2. Apply the move.
  3. Write the state with current = to, transition = None.

If a process dies between 1 and 3, the next bisect command sees transition and re-applies the move from from to to. Files already written equal to's versions, and the guard's plan treats bytes equal to the incoming version as current (Vault__Pull__Guard.plan), so the retry writes only what is left. reset does the same before returning to the head.

5.6.2 --no-checkout

Like Git's --no-checkout (which keeps BISECT_HEAD instead of moving HEAD): nothing is written; current moves and is shown. The run command gets SGIT_BISECT_COMMIT (5.8). During the bisect, sgit cat <path> and sgit ls read the commit under test (5.9), so a script can do sgit cat src/app.py | … with no checkout. This is the agent-friendly mode and the cheapest on a 76,000-file vault.

5.7 reset

  1. If a transition is recorded, finish it (5.6.1).
  2. Move the working copy from current back to the clone head (5.6), with the same guard: dirty files that the move would overwrite refuse the reset, naming them (--force overwrites, as git bisect reset does not need; we keep the guard by default because sgit has no index to protect them). Not touching the head's other files means a bisect on a 76,000-file vault resets in the time of its last diff.
  3. Delete bisect.json.
  4. reset <commit> (Git: "go to this commit instead of the original branch"): after 1–3, Vault__Sync__Pull.reset (directory, commit) (Vault__Sync__Pull.py:24), the existing history reset, which moves the clone ref and writes the reflog. That is the only path in this design that moves a ref, and it is an explicit user request.
  5. If bisect.json is unreadable, current is unknown, and reset cannot tell the user's edits from files the bisect wrote. It compares the disk with the clone head's flat (_scan_local_directory against flatten(head)), refuses, and lists the paths that differ; --force writes the head's version of each. Commits are never at risk: no ref moved.

If the clone head moved during the bisect (it cannot through sgit, 7.1, but a second process or a manual ref edit could), reset still returns to the current head and says your branch head moved during the bisect (from X to Y).

5.8 run

Loop:

if status is WAITING:      refuse: "bisect run needs a good and a bad commit first"
first = True
while status == BISECTING:
    r = Runner.run(argv, cwd=directory, env=env(current), timeout, shell)
    if r.aborted (exit < 0 or >= 128, or timeout):   print Git's message; exit with that code (state kept)
    code = r.exit_code
    if first and code in (126, 127):
        # Git's check: is the command itself broken? run it once on a good commit
        move working copy to good[0]; r2 = run(...); move back to current
        if r2.exit_code == code: error "bogus exit code {code} for good revision"; exit 1
    first = False
    verdict = GOOD if code == 0 else SKIP if code == 125 else BAD

return 0 if FOUND, 2 if ONLY_SKIPPED, 1 if MERGE_BASE_BAD

Vault__Bisect__Runner.run:

  • argv, never a shell string. subprocess.run([str(a) for a in argv], cwd=directory, env=env, timeout=timeout, stdin=subprocess.DEVNULL), output passed through to the terminal (not captured), as Git does. A missing binary is 127 (the Container__Command_Runner rule, :21).
  • --shell (sgit extra, explicit): ['/bin/sh', '-c', ' '.join(argv)] on POSIX, ['cmd', '/c', …] on Windows. Git always runs through the shell; sgit makes the shell opt-in so a path or a vault file name in the arguments is never interpreted (decision D3).
  • env: a copy of os.environ plus SGIT_BISECT_COMMIT=<current>, SGIT_BISECT_BAD=<bad>, SGIT_BISECT_STEP=<n>, SGIT_BISECT_TERM_OLD, SGIT_BISECT_TERM_NEW. Never the vault key, read key, write key or token: those are not added, and the variables sgit itself reads for secrets are not set by bisect.
  • cwd: the vault directory (the working copy root), as Git runs in the worktree.
  • timeout (sgit extra): --timeout SECONDS; a timeout kills the process group and counts as an abort (exit 124 printed, run exits 124). Decision D5 offers "count it as skip" instead.
  • Ctrl-C: KeyboardInterrupt stops the loop, state kept, exit 130.
  • Each run prints running <argv joined with shlex.join>.

5.11 Compatibility

  • No format change, no gate. Nothing is written to the vault or the host. Old clients, the web UI and other clones see nothing.
  • An older sgit run inside a folder with a bisect in progress does not know bisect.json: its status would show the bisect commit's files as modifications and its commit would commit them. The guard against that is the user's, as with any local tool mix; sgit update is the remedy. Noted in the CHANGELOG entry.
  • The local/index/generations.json memo is created on loose vaults too. It is a derived cache that Vault__Pack_Index already treats as such.

6.2 State tampering

bisect.json is local. Whoever can write it can already write the working copy and the refs. What a damaged or edited state can and cannot do:

  • It cannot move a ref, push or delete a commit: bisect has no code path that writes a ref (except reset <commit>, an explicit user request through the existing history reset).
  • Ids in it are re-validated on read (Safe_Str__Commit_Id) and must exist in the store; an unknown id refuses with bisect state names a commit this clone does not have: sgit history bisect reset.
  • Paths in it (paths) are used only for matching, never joined to the disk path without Vault__Path_Guard.safe_join.
  • A replay log (replay <file>) is untrusted text. Vault__Bisect__Log.parse accepts only lines matching ^(sgit history bisect|git bisect) (start|good|bad|old|new|skip|terms|<term>)( .*)?$ and # comments; every id is resolved through Vault__Revision.resolve (local only). Nothing in the file is executed; run lines are refused with a message.

6.3 No network writes during a bisect (proof)

  • By construction. The only network calls in the bisect code are api.batch_read and api.read_large, for blobs a loose sparse clone lacks (5.6, step 4). Vault__Sync__Bisect gets api only to pass it to that download. No code path in core/actions/bisect/ calls write, batch (the write batch), delete, presigned_*, the branch index writer, Vault__Ref_Manager.write_ref, push or pull. A unit test greps the package's source for those names (test_Bisect__No_Write_Calls), so a later change that adds one fails.
  • By test. test_Bisect__Nothing_Leaves_The_Clone runs a full run bisect over a two-clone setup on Vault__API__In_Memory and asserts:
  • api._store (Vault__API__In_Memory.py:11) is byte-identical before and after;
  • the clone's ref files, remote_heads.json, the local branch index file and reflog.jsonl are byte-identical;
  • the other clone's pull afterwards reports nothing new.

8. Performance

  • Steps: ⌈log2(n)⌉ for n candidates; 1,000 commits → about 10 steps.
  • Candidate set: one walk per command over commits between bad and the goods, with generations memoised in generations.json. Decrypting a commit is about 0.1–0.3 ms; 10,000 commits ≈ 1–3 s once, then the memo makes it near-instant. Weights: linear O(n); DAG bitsets O(n²/8) bytes (12.5 MB at 10,000), done in ms in Python integer ops.
  • A step's working-copy cost follows the change between two commits, not the vault. diff_trees opens only differing folders; the guard verifies only touched paths (_scan_local_directory(verify=touched)); only changed files are written. On the 76,000-file vault (58,553 folders), a step between commits that differ by 300 files costs about what a 300-file pull's write costs (the pull of a 300-file pass measured 16.9 s in total, most of it fetch and flatten that a bisect step does not do). The first step from the head can be large (half the history's changes); later steps halve.
  • Status during a bisect flattens the commit under test once; _flatten_incremental (Vault__Sub_Tree.py:186) derives it from a cached neighbour. The on-disk flat cache keeps two heads (FLAT_CACHE_ON_DISK = 2), so a long bisect evicts the head's entry; after reset the head is re-derived incrementally. Acceptable; no change.
  • --no-checkout writes nothing: a step is the graph work plus whatever the test reads with sgit cat.
  • Measure on the 76,000-file synthetic vault before release: start + 10 marks with and without --no-checkout, recorded in the CHANGELOG.

11. Open decisions for Dinis

#DecisionOptionsRecommendation
D1Commits during a bisect(a) refuse; (b) allow, as Git does on a detached HEAD (where reset orphans them)(a) refuse. In sgit a commit moves the clone branch itself, so "allow" would mean committing an old tree onto the branch: a silent revert
D2Custom-term syntax(a) exact Git syntax (sgit history bisect fixed) via one REMAINDER parser and our own dispatcher; (b) fixed argparse sub-parsers plus mark <term>(a): Git parity, and bisect's grammar is small enough to dispatch by hand; --help text is written by CLI__Bisect
D3run and the shell(a) argv by default, --shell opt-in; (b) always a shell, as Git(a). Same power (--shell 'make test && ./check'), no surprise interpretation of a file name
D4Pathspec on merges(a) the approximation in 5.3 (a merge counts when it differs from every parent); (b) port Git's full history simplification(a) now; it equals Git on linear history and is documented. Revisit if someone bisects path-limited merge-heavy histories
D5--timeout result(a) abort the run (state kept, exit 124); (b) count as skip(a): a hang usually means the test is broken, not the commit; skip would quietly widen the answer
D6What history log shows during a bisect(a) the clone head (unchanged); (b) the commit under test, like Git's git log on a detached HEAD(a), plus bisect view; keeps history log meaning "my branch"
