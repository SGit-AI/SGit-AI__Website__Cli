Design 01: line-level three-way merge (opt-in) and sgit history cherry-pick

Date2026-10-28 · 03:06 UTCKinddesignResearch topicsgitWritten bythe sgit-ai CLI team (Claude Code sessions), for Dinis CruzSourceteam/humans/dinis_cruz/claude-code-web/10/28/design__01__line-merge-and-cherry-pick.md in SGit-AI__CLI at 036e33b. Published here as written; the CLI repository is where the work happened.

Read with design__00__index-and-reconciliation.md: where the two disagree (shared foundations F1–F9, the in-progress rules), the index wins.

Roadmap items: 2.1 (line-level merge) and 2.8 (cherry-pick), from roadmap__git-parity.md (same folder). Status: design. No code has been written. Code read at: 3a1d72a (branch claude/charming-babbage-5hzcxq). Git behaviour checked: git 2.43.0 in this sandbox, using git merge-file (outputs quoted below).

In one paragraph. Today every sgit merge compares files by blob id. When both sides changed a file, sgit keeps ours and writes theirs next to it as <path>.conflict. That stays the default. A new opt-in style, lines, runs a Git-compatible three-way line merge on exactly those files. A clean result becomes a new blob in the merge commit. A rough edge becomes Git's <<<<<<< ======= >>>>>>> markers in the file itself.

  • Where the style is chosen: per command (--merge lines|files on pull and branch merge), or per clone (merge_style in .sg_vault/local/config.json).
  • What it touches: the vault format does not change. A merge result is an ordinary commit, so there is no version gate, and old clients and the web UI are unaffected.
  • Cherry-pick: sgit history cherry-pick <commit> is the same three-way merge with base = the picked commit's parent, ours = HEAD and theirs = the picked commit. It obeys the same style.

2. Scope and non-goals

In scope

  1. A line-level three-way merge engine (Vault__Line_Diff, Vault__Line_Merge) on bytes, with conflict styles merge and diff3.
  2. Opt-in style selection:
  • flag --merge lines|files on pull and branch merge;
  • per-clone default merge_style in Schema__Local_Config;
  • optionally the environment variable SGIT_MERGE_STYLE (decision D1).
  • The default stays files (today's behaviour, byte for byte).
  1. The same engine is used, when lines is selected, by the other three callers of three_way_merge: the rewind re-apply (Step__Pull__Merge._take_rewind), history revert --as-commit and the new cherry-pick.
  2. Conflict handling for marker files:
  • merge state records which paths hold markers;
  • commit refuses while complete marker blocks remain;
  • resolve <file> marks a hand-edited file resolved;
  • resolve --ours/--theirs restores a side;
  • merge-abort restores ours.
  1. sgit status shows an in-progress merge. It does not today (§4.6).
  2. sgit history cherry-pick <commit>… with -x, --continue, --abort, --json.
  3. The pre-existing defect found while checking (§4.5): commit while .conflict files exist commits the .conflict files into the vault. Fixed for both styles (decision D3).

Non-goals (this round)

  • zdiff3, a configurable marker size, -X ours/theirs/union per hunk. The engine supports ours/theirs/union internally for tests, not on the CLI.
  • The histogram or patience diff, and the indent heuristic.
  • The recursive merge-base (virtual base) for criss-cross histories. find_lca keeps returning one LCA (Vault__Fetch.find_lca, sgit_ai/core/actions/fetch/Vault__Fetch.py:78).
  • Rename detection (item 2.4). Merge attributes or .gitattributes. Per-file merge drivers.
  • cherry-pick -m <parent> (merge commits are refused), commit ranges A..B, --skip, -n/--no-commit, --edit.
  • Pull --json; the pull exit code (stays 0 on conflicts, decision D6).
  • The web UI's merge. It keeps whole-file .conflict semantics and is not touched.

Refusals (Vault__Revision_Error, exit 1, nothing written):

  • a merge commit: <id> is a merge commit; cherry-pick of merges is not supported;

4. How the code works today

4.1 The classifier

sgit_ai/core/actions/merge/Vault__Merge.py:14-80, three_way_merge(base_map, ours_map, theirs_map).

  • Inputs: flat maps {path: {blob_id, size, content_hash, content_type, large}}.
  • Rule: per path, compare blob ids only:
  • neither side changed → ours;
  • one side changed → that side;
  • both changed to the same blob → ours;
  • both changed differently (:47-49) → ours plus a conflict;
  • add/add with different blobs (:57-60) → ours plus a conflict;
  • modify/delete and delete/modify (:63-71) → the modified side plus a conflict.
  • Returns: merged_map, conflicts, added, modified, deleted.

write_conflict_files (:82-106) decrypts theirs' blob to <path>.conflict, through Vault__Path_Guard.safe_join. It skips silently when theirs has no entry (ours modified / theirs deleted) and on any exception. CONFLICT_SUFFIX = '.conflict' (:8; duplicated as Vault__Sync__Base.py:31, pinned equal by a test).

4.5 Commit during a merge, and a defect

Vault__Sync__Commit.commit (sgit_ai/core/actions/commit/Vault__Sync__Commit.py:147-197):

  • reads the merge state;
  • has_conflict_files = any *.conflict file seen by the scan (Vault__Sync__Base.py:569-570);
  • with a state and no .conflict files: a merge commit (second parent = theirs_commit_id) and the state is deleted;
  • with .conflict files present, it commits anyway, as a single-parent commit, and keeps the state.

*.conflict is not in any ignore rule (Vault__Ignore.py:6-27 ignores folders only), so the .conflict files themselves are committed.

Reproduced here: pull → conflict on shared.txt → sync.commit(..., 'while conflicted') returned files_changed: 1, merge_commit: False, and that one file is shared.txt.conflict. After resolve shared.txt --theirs the next commit had files_changed: 2 (the .conflict deleted, shared.txt changed) and merge_commit: True. Every teammate who pulls between the two commits receives shared.txt.conflict.

4.6 Status and the CLI

  • Status: Vault__Sync__Status.status returns merge_in_progress, merge_ours/theirs/lca, merge_conflicts, merge_resolved (sgit_ai/core/actions/status/Vault__Sync__Status.py:215-228). CLI__Vault.cmd_status (sgit_ai/cli/CLI__Vault.py:826+) prints none of it, although the pull output says "See unresolved conflicts: sgit status".
  • Pull exit code: pull prints conflicts and returns normally, so it exits 0 (CLI__Vault.cmd_pull, :995-1009).

4.7 Blobs and entries

  • Writing a blob: Vault__Sub_Tree.encrypt_or_reuse_blob(content, old_entry, read_key) (sgit_ai/storage/Vault__Sub_Tree.py:517-529):
  • content_hash = sha256(plaintext)[:12] (Vault__Crypto.content_hash, Vault__Crypto.py:335);
  • a blob whose hash matches the old entry is reused;
  • otherwise crypto.encrypt(read_key, content, deflate=True) (deflated on a blob-deflate vault) and obj_store.store;
  • large = ciphertext > 4 MiB (LARGE_BLOB_THRESHOLD, :9).
  • Building trees from a merged map: build_from_flat(flat_map, read_key, opaque=…) (:105-130) uses each entry's blob_id, size, content_hash, content_type and large.
  • Reading: obj_store.load + crypto.decrypt handle both envelopes and pack-store clones transparently.
  • Push: it collects the blobs of every commit in the pushed chain, so a new merge blob is uploaded with the merge commit.

4.8 The dirty-tree guard and selective writes

  • The guard: Step__Pull__Merge._guard_working_tree (:327-362) computes touched = paths whose blob differs between ours_map and merged_map, scans with verify=touched, and refuses (Vault__Dirty_Working_Tree_Error) before any write if a dirty path would be overwritten. blocked_targets also refuses untracked files in the way.
  • Today's blind spot: .conflict targets are not checked, so an untracked x.conflict is overwritten.
  • Selective writes: _write_selective (:218-230) writes through Pull__Selective.split (selective working copies) and records the writes (after_write).

4.9 Blob availability

  • Step__Pull__Fetch_Missing fetches theirs' commits and trees, and blobs unless the clone is --sparse (include_blobs = not is_sparse, Step__Pull__Fetch_Missing.py:124).
  • On a scoped clone, only the scope is fetched.
  • Base blobs (the LCA's) are local whenever the clone held that commit's files. That is not the case for --sparse, or across a shallow boundary.
  • Vault__Sync__Sparse.sparse_fetch + _save_verified (sgit_ai/core/actions/sparse/Vault__Sync__Sparse.py:106-175, 262-271) is the existing verified on-demand blob fetch: api.batch_read for small blobs, api.read_large for large ones, and Vault__Verified_Write.

4.10 Diff code in the tree

Vault__Diff uses difflib for display and _is_binary = a NUL in the first 8,192 bytes (sgit_ai/core/actions/diff/Vault__Diff.py:24,534-535). three_way_conflict_view (:664+) powers resolve --show. No three-way line-merge code exists.

5.3 The diff: Vault__Line_Diff

Input preparation (in Vault__Line_Merge)

  1. Split each side with Vault__Line_Splitter.split. A line is the bytes up to and including \n; the last line may lack it. \r stays part of the line, so a\r\n ≠ a\n, as in Git without whitespace options.
  2. Intern every distinct line (bytes, including the eol) to a small int with one dict shared by the three files. The diff then compares ints.

Algorithm: Myers 1986, "An O(ND) Difference Algorithm", linear-space variant (§4b, the middle-snake divide and conquer, as xdiff's xdl_split). Steps:

  1. Trim the common prefix and suffix (xdiff's xdl_trim_ends). This is O(n) and removes most work on real files.
  2. Discard lines with no match (xdiff's xdl_cleanup_records, simplified): a line id that occurs only in A (or only in B) can never be in the LCS. Mark it as changed up front and run Myers on the remaining subsequences, keeping an index map back to the originals. This is a large speed-up for "mostly different" files.
  3. Middle snake recursion on the remaining ranges. Each find_middle_snake(a_lo, a_hi, b_lo, b_hi) runs the forward and backward greedy searches with two V arrays of size 2·max_d + 1 (Python lists of ints), stops at the first overlap, and recurses on both halves. Memory is O(N+M).
  4. Cost cap: a running count of the edit cost D per top-level call. If D exceeds MAX_EDIT_COST = 5,000 (lines added + removed), the diff stops with Vault__Line_Diff__Too_Different. Vault__Line_Merge turns that into outcome TOO_DIFFERENT, and the path falls back to the whole-file conflict. (xdiff instead switches to a heuristic split; we prefer a clear fallback: decision D8.)
  5. Produce hunks: walk the edit script and emit maximal Schema__Line_Hunk(base_start, base_end, side_start, side_end). A pure insertion has base_start == base_end; a pure deletion has side_start == side_end.
  6. Compaction (deterministic placement in ambiguous runs, xdiff's xdl_change_compact without the indent heuristic): for each group of changed lines in A (and separately in B), slide it down while the line after the group equals the group's first line, then back up only if that aligns it with a change group on the other side. Git applies the same rule. This makes the output deterministic. Exact equality with Git on repeated-line inputs is not promised (§9.3).

Interface:

class Vault__Line_Diff(Type_Safe):
    max_edit_cost : Safe_UInt__Line_Number = 5000
    def diff(self, a_ids: list, b_ids: list) -> list            # list[Schema__Line_Hunk], sorted by base_start

Raises Vault__Line_Diff__Too_Different(Exception) (in sgit_ai/core/Vault__Errors.py).

5.4 The merge: Vault__Line_Merge (xdiff xdl_merge semantics)

Pre-checks, in order (each returns (b'', result) with the outcome and a reason):

CheckOutcome
any side is_binaryBINARY
any side longer than MAX_MERGE_BYTES = 8 MiB, or more than MAX_MERGE_LINES = 200,000 linesTOO_LARGE

Step 1: two diffs. H_o = diff(B, O) and H_t = diff(B, T), as base-relative hunks.

Step 2: walk both hunk lists in base order and group. Let i, j index H_o and H_t.

  • If H_o[i].base_end < H_t[j].base_start, the ours hunk is strictly before theirs, with at least one unchanged base line between. Emit it as a one-sided change (ours) and advance i. Symmetrically for theirs.
  • Otherwise the hunks overlap or touch (end == start counts, G4; two insertions at the same point overlap, G6). Open a group with g_lo = min(starts) and g_hi = max(ends). Keep absorbing the next hunk from either list while its base_start <= g_hi, extending g_hi.
  • For each group, map the base range [g_lo, g_hi) onto each side. With δ_o(k) = the sum of (side_len − base_len) over the ours hunks ending at or before base line k:
  • ours_lo = g_lo + δ_o(before group);
  • ours_hi = g_hi + δ_o(through group);
  • likewise for theirs;
  • a side with no hunk in the group gets the base lines, i.e. its range is the base range shifted by its δ.
  • EAGER: if O[ours_lo:ours_hi] == T[theirs_lo:theirs_hi] (identical change, G3/G7), emit it as a non-conflict.
  • Otherwise emit Conflict(base=[g_lo,g_hi), ours=[ours_lo,ours_hi), theirs=[theirs_lo,theirs_hi)).

Step 3: refine, ZEALOUS (merge style only, not diff3; Git caps diff3 at EAGER, G9). For each conflict where both sides are non-empty, diff the ours text against the theirs text. Equal runs become non-conflict lines; each differing region becomes its own smaller conflict. Its base range is the whole original base range for the first sub-conflict and empty for the rest, as in xdiff's xdl_refine_conflicts; base is only printed in diff3 style, which skips this step.

Step 4: simplify, ZEALOUS_ALNUM (merge style only). Walk adjacent conflicts c1, c2 in ours coordinates. Let gap = the ours lines between c1.ours_hi and c2.ours_lo. Merge them when len(gap) <= 3 (G10/G11) or when no gap line contains an ASCII alphanumeric byte [0-9A-Za-z] (G12). The merged conflict:

  • ours = from c1.ours_lo to c2.ours_hi;
  • theirs = the matching span in theirs coordinates, including the same gap lines (they are common text);
  • base = the span covering both.

Repeat until stable.

Step 5: assemble the output. Walk the base in order:

  • unchanged base lines → copied;
  • a one-sided ours or theirs change → that side's lines;
  • a resolved identical change → those lines;
  • a conflict → the block below.

The marker size is 7 and eol = \r\n when CR is needed, else \n:

<<<<<<< {labels.ours}{eol}
{ours lines}
||||||| {labels.base}{eol}        ← diff3 style only
{base lines}                      ← diff3 style only
======={eol}
{theirs lines}
>>>>>>> {labels.theirs}{eol}
  • No final newline (G14): if a side's block is non-empty and its last line has no \n, append eol before the next marker. The output then always ends a conflict with >>>>>>> …{eol}.
  • When CR is needed (G13): as xdiff's is_cr_needed. Look at the line before the conflict in ours (or ours' first line if the conflict starts at 0): it must end in \r\n, and the same must hold in theirs. If either side is undetermined (no eol at all), use base's. Otherwise \n.

Step 6: the result. No conflicts → outcome = CLEAN, content = the assembled bytes. Otherwise outcome = CONFLICT, hunks = the number of conflict blocks after simplification. This equals git merge-file's exit code below 128.

Labels, built by the caller and sanitised by Safe_Str__Conflict_Label:

Operationoursbasetheirs
pullours (this clone {12-hex})base ({12-hex of LCA})theirs ({named branch name} {12-hex})
branch mergeours (this clone {12-hex})base ({12-hex})theirs ({merged branch name} {12-hex})
cherry-pickHEAD ({12-hex})parent of {12-hex}{12-hex} ({first 50 chars of the subject})

A subject is untrusted vault data. Every character outside printable ASCII becomes _, and the label is truncated to 80 characters, so it can never start a new line or contain a marker on its own line.

Internal options, for tests only: favor: ours|theirs|union resolves every conflict to one side or both (Git's --ours/--theirs/--union, G-oracle), used by property tests. No CLI flag.

5.5 The bridge: Vault__Content_Merger

class Vault__Content_Merger(Type_Safe):
    crypto         : Vault__Crypto
    obj_store      : Vault__Object_Store

    labels         : Schema__Conflict_Labels
    blob_fetcher   : object = None          # callable(list[blob_id]) -> None; fetches and verifies missing blobs

merge_entry steps:

  1. If ours or theirs has no entry (modify/delete): return NOT_TEXT_PAIR (the classifier keeps today's rule).
  2. Collect the blob ids (base is None for add/add). Missing locally ones go to blob_fetcher (one batch). If any is still missing: MISSING_BLOB.
  3. Decrypt them (crypto.decrypt(read_key, obj_store.load(id))). Base = b'' for add/add, as Git does.
  4. line_merge.merge(...).
  5. Clean: blob_id, large, content_hash = Vault__Sub_Tree.encrypt_or_reuse_blob(content, ours_entry, read_key). A result equal to ours reuses ours' blob. The new entry is:
  • blob_id;
  • size = len(content);
  • content_hash;
  • content_type = ours_entry.content_type or theirs_entry.content_type;
  • large.

Return CLEAN with the entry's blob_id.

  1. Conflict: return CONFLICT with kind = MARKERS and the marker bytes. Nothing is stored in the object store: markers never become a blob until the person commits them, and the commit guard (§5.8) refuses that.
  2. Anything else: return the outcome. The classifier falls back to WHOLE_FILE.

5.9 Cherry-pick: Vault__Cherry_Pick

pick(directory, specs, record_origin=False, merge_style=None, conflict_style=None) -> dict

  1. Guards:
  • the clone is not read-only;
  • no merge state (check_not_in_progress(directory, 'cherry-pick'));
  • the working copy is clean (Vault__Sync__History_Edit._require_clean, reused through a shared base method);
  • the clone has a head.
  1. Resolve every spec with Vault__Revision.resolve_soft. For a full id that is not local, fetch it with _fetch_missing_objects(commit_id=<id>, stop_at=<head>, include_blobs=True). That walks the picked commit's ancestry until it meets local commits; already-local objects are skipped.
  2. Signature policy: if the vault has signatures-required, every picked commit must verify (Vault__Signatures. status_of(...) == VERIFIED) under the same rule pull applies (Vault__Incoming_Check). Otherwise Vault__Signature_Error names the commit. See §6, threat T3.
  3. For each commit P, in order:
  • refuse a merge commit;
  • base_map = flatten(P.parent.tree), or {} for a root commit; ours_map = flatten(HEAD.tree); theirs_map = flatten(P.tree). Scoped clones use Vault__Scoped_Tree.flatten and carry theirs_opaque from HEAD, not from P (§7);
  • merger as §5.7 with the cherry-pick labels; three_way_merge(base, ours, theirs, content_merger=…);
  • empty (merged blob map == ours' blob map): stop with status empty and exit 1, writing nothing;
  • guard: _guard_working_tree-equivalent dirty check (the working copy is clean, but the check also catches untracked files in the way: Vault__Pull__Guard.blocked_targets);
  • write the working copy (deletions first, then merged_map entries that differ from ours) with _remove_deleted_flat and _checkout_flat_map, as revert does (Vault__Sync__History_Edit.py:95-96);
  • conflicts: write the .conflict and marker files and the merge state, with:
  • operation = cherry-pick;
  • ours_commit_id = HEAD;
  • theirs_commit_id = P;
  • lca_id = P's parent;
  • source_commit_id = P;
  • remaining_commit_ids = the specs not yet applied;
  • sequence_start_id = HEAD before the first pick;
  • record_origin.

Stop with status conflicts;

  • clean: build the tree (build_from_flat, with opaque on a scoped clone), then create_commit(parent_ids=[HEAD], message=pick_message(P, record_origin), signing_key=…) signed with the clone key exactly as commit does (Vault__Sync__Commit._load_signing_key), write the ref, and record the reflog entry cherry-pick: <subject>.
  1. Return {status, picked, commit_ids, remaining, stopped_at, files, conflicts}.

pick_message(P, record_origin): P's decrypted message (crypto.decrypt_metadata(read_key, P.message_enc)), falling back to Cherry-pick <12-hex> when undecryptable. With record_origin, append \n\n(cherry picked from commit <full id>).

continue_(directory):

  • requires a state with operation == cherry-pick;
  • runs the unresolved check of §5.8; unresolved paths → Vault__Merge_Unresolved_Error;
  • commits the working copy as a single-parent commit with pick_message(source, record_origin). To do that without duplicating code, it calls Vault__Sync__Commit.commit(directory, message=…, no_merge_commit=True); no_merge_commit already exists (Vault__Sync__Commit.py:33,153). The new commit refuses when the working copy equals HEAD ("now empty": status empty);
  • deletes the state;
  • if remaining_commit_ids is not empty, calls pick(directory, remaining, …) with the same options.

abort(directory): Vault__Merge__Abort with ours_commit_id := sequence_start_id. Earlier successful picks in the same sequence are undone too, as git cherry-pick --abort does.

Commit attribution: the new commit is authored and signed by this clone, like every sgit commit. The original author survives only in the -x trailer and in history log of the source commit. Git keeps author separate from committer; sgit has no author field (D7).

This is the same shape as revert's scoped refusal (Vault__Sync__History_Edit.py:63-65), but narrower: allowed when P stays in scope.
Shallow cloneIf the LCA lies beyond the boundary, find_lca returns None, so base_map = {} and every both-present differing path is add/add (base b'', G16), as today's classifier already does. Cherry-pick of a commit whose parent is beyond the boundary: refused (Vault__Revision._parent already names the shallow case, Vault__Revision.py:158-161).
Sparse clone (--sparse)Blobs are not fetched by pull. The merger fetches the base, ours and theirs blobs of only the both-changed paths, verified (§5.7 step 2). Offline → MISSING_BLOB → whole-file fallback with the reason printed.

8. Performance

Where the cost goes. The classifier (three_way_merge) is unchanged and O(paths). The line engine runs only on paths both sides changed to different blobs. Measured workloads:

Engine targets, pure Python on the 4-core sandbox; benchmarks in Test_Vault__Line_Merge__Perf, marked slow and excluded from -n auto unit runs by name filter only if needed:

Binary or over-cap detectionO(8,000 bytes) / O(1) via the entry's size before decrypting: an entry whose size field exceeds 8 MiB is TOO_LARGE without loading the blob

Memory: linear-space Myers, O(N+M) ints, plus the three byte strings (≤ 3 × 8 MiB).

Cherry-pick: three flattens (base, ours, theirs). On a pack vault with indexes these come from the flat cache or the index (flat_of). On the 76,000-file vault a flatten from cache is ≈0.5 s, so ≈1.5 s plus the classification, before any line merge.

No effect on files style: byte-identical code path (content_merger=None).
