1. Summary and the exact Git behaviour matched

1.1 In one paragraph

Rebase replays this clone's own commits that the named branch does not yet hold on top of another commit, usually the named branch's newest head. Each replayed commit is a cherry-pick: the change it made relative to its parent is applied to the new tip. Merge commits in the range are dropped and the history becomes linear. Commits whose change is already upstream are skipped. A conflict stops the rebase with the state saved; the user resolves and runs --continue, or --skip, or --abort to get exactly back to where they were. pull --rebase fetches (with every existing guard) and then rebases instead of merging. Interactive mode (-i) edits a todo list: pick, reword, edit, squash, fixup, drop, exec. Agents give the todo as a file or JSON, with no editor.

Two sgit rules on top of Git:

  1. Rebase never rewrites a commit the server already has. Every commit in the todo must be unreachable from the named head this clone holds and from the remote head it last accepted (its baseline). This is the rule commit --amend and history undo already use (Vault__Sync__History_Edit.is_pushed, sgit_ai/core/actions/history/Vault__Sync__History_Edit.py:26-36). Because of it, the next push is always a fast-forward of the named branch, and no other clone ever sees a rewind.
  2. A replayed commit is signed by this clone, like every commit sgit makes. A commit signed by another clone's key is not replayed unless the user asks (--allow-foreign), because replaying would re-attribute it.

2. Scope and non-goals

In scope (v1):

  • sgit history rebase [<upstream>] with --onto, --keep-base, -i, --todo FILE|-, --exec, --autosquash, --autostash, --empty, --reapply-cherry-picks, --merge/--conflict (design__01), --reset-date, --allow-foreign, --no-verify, --sign/--no-sign (design__02), --dry-run, --json.
  • --continue [-m MSG], --skip, --abort, --quit, --show-todo, --edit-todo.
  • Todo actions: pick, reword, edit, squash, fixup (with -C/-c), drop, exec, break.
  • sgit pull --rebase / --no-rebase / --autostash; per-clone pull_rebase; push's implicit pull follows it.
  • ORIG_HEAD; reflog reasons; status shows a rebase in progress.
  • A tree-spine builder Vault__Sub_Tree.apply_changes so a replayed commit costs what it changed, not the vault.

3. CLI surface

3.1 Placement (Rule 9)

  • sgit history rebase. Rebase rewrites commits, and CLAUDE.md rule 9 puts "anything about commits under history" (log, reset, reflog, undo, revert are there: sgit_ai/plugins/history/CLI__History.py:70-170). TOP_LEVEL_COMMANDS (tests/unit/cli/test_CLI__B07__Namespace_Moves.py:104-109) does not change.
  • sgit pull --rebase. A flag on the existing top-level daily verb, as in Git.
  • rebase joins "commands" in sgit_ai/plugins/history/plugin.json.

Decision D1 asks whether a top-level sgit rebase alias is wanted. The recommendation is no: pull --rebase covers the daily case, and Git users find history rebase by sgit help history.

3.4 Todo formats

Text (Git's format, so -i feels familiar). File: .sg_vault/local/rebase/todo.

pick 3f9a1c2b7e01 Add the field
reword 9b2c4d5e6f70 Fix typo in README
edit 0a1b2c3d4e5f Split parser
squash 7e7e7e7e7e7e squash! Add the field
fixup -C 4c4c4c4c4c4c Better message for the fixup
drop 5d5d5d5d5d5d WIP
exec pytest -q tests/unit/schemas
break

# Rebase 1d2c3b4a5e6f..3f9a1c2b7e01 onto 1d2c3b4a5e6f (6 commands)
#
# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = use commit, but meld into previous commit
# f, fixup [-C | -c] <commit> = like "squash" but keep only the previous
#                    commit's message, unless -C is used, in which case
#                    keep only this commit's message; -c is same as -C but
#                    opens the editor
# x, exec <command> = run command (an argv, split like a shell would, no shell)
# b, break = stop here (continue rebase later with 'sgit history rebase --continue')
# d, drop <commit> = remove commit
#
# Lines starting with # are ignored. An empty todo aborts the rebase.

Rules: one action per line; the commit is any prefix of 4+ hex characters after obj-cas-imm- that resolves uniquely among local commits (Vault__Revision._commit_by_prefix, Vault__Revision.py:128); the rest of a pick line is a comment. Unknown verbs and unresolvable commits refuse the whole todo before anything is written, naming the line.

JSON (agents). Same verbs; messages inline, so nothing has to stop for a reword:

{
  "todo": [
    {"action": "pick",   "commit": "3f9a1c2b7e01"},
    {"action": "reword", "commit": "9b2c4d5e6f70", "message": "Fix typo in README"},
    {"action": "edit",   "commit": "0a1b2c3d4e5f"},
    {"action": "squash", "commit": "7e7e7e7e7e7e", "message": "Add the field (with its tests)"},
    {"action": "fixup",  "commit": "4c4c4c4c4c4c", "use_message": "this"},
    {"action": "drop",   "commit": "5d5d5d5d5d5d"},
    {"action": "exec",   "argv": ["pytest", "-q", "tests/unit/schemas"]},
    {"action": "break"}
  ]
}

A bare JSON array is accepted too. fixup.use_message is previous (default, Git's plain fixup) or this (Git's -C). An exec takes argv (a list) or command (a string split with shlex.split). Validation is a Type_Safe parse into Schema__Rebase_Todo (5.2); any error refuses before anything is written.

reword with no message: interactive mode opens the editor; non-interactive mode stops with reason reword and waits for --continue -m MSG.

5. Design

5.1 Terms and invariants

TermMeaning
H / orig_headThis clone's head (its clone-branch ref) when the rebase starts.
U / upstreamThe commit whose ancestors are "already upstream". Default: the local named ref of the tracked named branch.
O / ontoWhere the replay starts. Default U; --onto X; --keep-base → merge base of U and H.
BThe set of baselines and held heads: {U} ∪ local named ref ∪ the accepted baseline for the tracked branch (_read_remote_baseline).

Invariants (each has a test in 9):

  • I1 (never rewrite pushed history). No commit in the todo is reachable from any commit in B. Checked when the todo is built and again for every todo commit an edited todo names.
  • I2 (local only). A rebase writes no server object and no remote ref. Only history rebase and the merge-free rebase step of pull --rebase run, and the pull part writes only what a pull writes today.
  • I3 (baselines untouched). remote_heads.json, last_remote_head and the local named ref are never written by the rebase engine.
  • I4 (atomic undo). After --abort: clone ref == orig_head, working copy == tree(orig_head) on the paths the rebase touched, no state files, the autostash popped. After a finished rebase, one history undo restores orig_head.
  • I5 (working copy == materialized). Outside a crash window, the working copy holds tree(materialized) plus only the conflict files of the current stop, and the clone ref == materialized.
  • I6 (identical trees). A tree built by apply_changes has the same id as build_from_flat on the same flat map (tests compare both).
  • I7 (cost follows the change). A replay step opens only the folders on the changed paths.

5.4 Building the todo

New class Vault__Rebase__Planner(Type_Safe) in sgit_ai/core/actions/rebase/Vault__Rebase__Planner.py.

5.4.1 The range

plan(directory, c, upstream_spec, onto_spec, keep_base, reapply, allow_foreign) -> Schema__Rebase_Plan

  1. Resolve. H = clone ref (Vault__Revision.head). U = resolve_soft(upstream_spec), or the local named ref of the tracked named branch (branch_manager.tracked_named_branch as in is_pushed, Vault__Sync__History_Edit.py:30-34). No upstream and no argument: refuse ("this clone has never pulled its named branch: name a commit to rebase onto").
  2. Held heads B = {U, local named ref, _read_remote_baseline(tracked named ref)} minus empty.
  3. Range walk. A generation-ordered painting walk, Git's paint_down_to_common with generation numbers instead of commit dates (sgit timestamps are not monotonic once rebased commits keep their dates):
  • a max-heap of (generation, commit_id) seeded with H (flag OURS) and each of B (flag HELD);
  • pop the highest generation; if it carries HELD, propagate HELD to its parents; else propagate OURS; a commit reached with both flags is HELD;
  • stop when every entry still in the heap is HELD (all "stale");
  • the range is every popped commit flagged OURS only;
  • generations come from Vault__Pack_Index.generation_of (Vault__Pack_Index.py:137), memoised per clone, so the walk is exact on loose and pack vaults and costs one commit decrypt per commit once per clone.

This walk is the one design__05 specifies in Vault__Bisect__Graph.candidates (design__05__bisect.md:277-283). Proposal (decision D9): move it into sgit_ai/core/actions/history/Vault__Commit_Graph.py (parents, generation, paint(include, exclude) -> dict, range(include, exclude) -> list, merge_bases(a, b) -> list) and have bisect and rebase both use it. The existing find_lca (200-ancestor limit, 4 above) is not used.

  1. Shallow boundaries. A boundary commit (Vault__Scope.boundary_ids()) has no local parents: the walk stops there. If the OURS side reaches a boundary that the HELD side never reached, the range cannot be proven (part of it may be upstream): refuse with "this shallow clone does not hold enough history to tell your commits from the upstream's; sgit fetch --unshallow". An unpushed range that sits wholly above the boundary always meets the held side first.
  2. Order. Topological, oldest first, ties by generation then by timestamp_ms then id (Git's --reverse --topo-order).
  3. Merges. Drop commits with more than one parent (Git's default; result = dropped is not recorded for them: they are simply not in the todo, as in Git).
  4. --keep-base. O = the single merge base of U and H (Vault__Commit_Graph.merge_bases); several bases: refuse naming them.
  5. Up to date. If the range is empty and O is an ancestor of H (or equal), the result is up_to_date: "Current head <H> is up to date." Exit 0, nothing written.
  6. Fast-forward. If the range is empty and H is an ancestor of O: move to O (no replay; reflog rebase (finish)), like Git's "Fast-forwarded".

5.4.3 Skipping commits already upstream (--reapply-cherry-picks off)

Git compares patch ids. sgit compares change signatures, computed from the plaintext content hashes that tree entries already carry (content_hash = sha256(plaintext)[:12], design__01 4):

signature(c) = sorted( (path, old content_hash or '-', new content_hash or '-') for each changed path )
             where the change set is Vault__Sub_Tree.diff_trees(c.tree, c.parent.tree)
  • Upstream side: every non-merge commit reachable from U and not from H (the HELD-only commits the painting walk popped above the merge base).   • A local commit whose signature is in the upstream set gets result = skipped_upstream and is left out of the todo (it appears in --dry-run and --json output).

5.4.4 Interactive and file todos

  • -i: write todo (3.4 format, comments included), run the editor (argv from shlex.split of the editor variable, plus the file path; no shell; inherited stdio; cwd = vault root), parse. Empty todo → abort quietly ("Nothing to do"), as Git does.
  • --todo FILE|-: parse text or JSON (3.4). Refusals happen before the state exists.
  • --autosquash: for each commit whose subject starts fixup! or squash!, move it after the last earlier commit whose subject equals (or starts with) the rest, turning pick into fixup/squash. Done before the editor opens, as in Git.
  • --exec: append exec items after each pick/reword/edit/squash group.
  • --edit-todo during a stop: rewrite the remaining todo (editor or --todo); checks of 5.4.2 re-run on the new items; done is untouched.

5.5 Replaying one commit

New class Vault__Rebase__Replay(Type_Safe) in sgit_ai/core/actions/rebase/Vault__Rebase__Replay.py. replay(c, state, item, tip) -> Schema__Rebase_Replay_Result with result : Enum__Rebase_Step_Result, new_tree_id, changes : dict (see below), conflicts, marker_conflicts, line_merged.

Let C be the commit, P its first (only) parent, T the current tip.

5.5.1 The change set

delta = Vault__Sub_Tree.diff_trees(C.tree_id, P.tree_id, read_key) (Vault__Sub_Tree.py:259). It returns added, deleted, modified by walking only the folders whose ids differ (I7). paths = added ∪ deleted ∪ modified.

On a pack vault whose commit index is present and verified, the commit index's change-list member gives the same set without a walk (Vault__Pack_Index__Reader); this is an optimisation behind the same interface, not a requirement.

5.5.2 The three sub-maps

For each p in paths:

  • base[p]: the entry in P (from delta: the old side of modified/deleted; absent for added);
  • theirs[p]: the entry in C (new side of modified/added; absent for deleted);
  • ours[p]: the entry at p in T, read with a new Vault__Sub_Tree.entry_at(tree_id, path, read_key) -> dict (a sibling of resolve_path_target, Vault__Sub_Tree.py:437-467, returning the flat entry dict or None, with a per-replay folder cache so siblings share loads).

5.5.3 Normalising equal content

Before classifying, for each p where ours[p] and theirs[p] (or base[p]) exist with equal content_hash and equal size but different blob_id: rewrite the blob_id of the later side to the earlier side's id (theirs[p].blob_id = ours[p].blob_id; base likewise). The random-IV blob encryption (4) otherwise makes "both sides made the same change" a conflict. 5.6 Vault__Sub_Tree.apply_changes (the spine rebuild)

apply_changes(root_tree_id: str, changes: dict, read_key: bytes) -> str in sgit_ai/storage/Vault__Sub_Tree.py. changes maps a vault path to a flat entry dict (add or replace) or None (delete).

  1. Group paths by parent folder; collect the set of affected folders = every ancestor of every changed path, including '' (the root).
  2. Load the affected folders that exist in the old tree, top-down along each path, with _load_tree_entries (Vault__Sub_Tree.py:326): decrypt each entry name once (_entries_by_name, :306). Missing folders (a new folder) start empty.
  3. Process affected folders deepest first:
  • for each changed file in the folder: set entries[name] = _entry_from_flat(name, entry, read_key) (:94-103), or delete it;
  • for each affected child folder: replace its entry with tree_id = new id, or delete the entry if the child became empty;
  • a folder with no entries left is not stored (its parent drops it). The builder never creates an empty folder, so ids still match;
  • order the entries exactly as _build_tree_from_dir_contents does (:556-642): files sorted by plaintext name, then folders sorted by plaintext name. Entries carried from the old tree keep their exact encrypted bytes, including out-of-scope siblings on a scoped clone;
  • new_id = _store_tree(Schema__Object_Tree(schema='tree_v1', entries=…), read_key) (:644, deterministic encryption, so the id is a content address).
  1. Return the new root id. If no change altered anything, return root_tree_id unchanged.

Equivalence (I6). For any tree T and change map Δ: apply_changes(T, Δ) == build_from_flat(flatten(T) ⊕ Δ). Tested with randomised trees (9.2). The fields that make up an entry (name_enc, size_enc, content_hash_enc, content_type_enc with the same fallback, large) come from the one helper _entry_from_flat, so the bytes are identical. Folder entries carry only tree_id and name_enc, as the builder writes them (:610-614).

Use elsewhere. design__01's cherry-pick and history revert --as-commit can use it too (follow-up; not required for this design).

5.7 The working copy: lazy, idempotent materialisation

New class Vault__Rebase__Working_Copy(Type_Safe) in sgit_ai/core/actions/rebase/Vault__Rebase__Working_Copy.py.

Why lazy. A rebase of ten commits that never stops does not need the ten intermediate working copies. The working copy and the clone ref move only when the user can see them: at a stop, before an exec, at the end, and on abort. On the 76,000-file vault this turns ten checkouts into one (8).

materialize(directory, c, state, target) -> dict:

  1. If target == state.materialized and state.materializing_to is empty: return.
  2. state.materializing_to = target; write state.
  3. change = diff_trees(target.tree, materialized.tree) → apply_map = added + modified (new side), deletions = deleted.
  4. Guard (only blocked targets; the tree was clean at start): Vault__Pull__Guard.blocked_targets(directory, writes, deletions) (Vault__Pull__Guard.py): an untracked or ignored file in the way refuses, naming it. Uncommitted edits at a stop (the user edited during edit/break) are handled by --continue before any materialisation, so they are never overwritten here.
  5. Write through the same code pull uses: the extracted Vault__Working_Copy__Writer.write(directory, read_key, selective, ours_map=materialized side, new_map=target side, apply_map). That is Step__Pull__Merge._write_selective (Step__Pull__Merge.py:218-230) moved into sgit_ai/core/actions/checkout/Vault__Working_Copy__Writer.py so pull, cherry-pick and rebase share it: deletions first, selective split, _refuse_unwritten on failure. The maps are the changed paths only (never full flattens).
  6. ref_manager.write_ref(clone_ref_id, target, read_key, reason=…, reflog_old=…) (5.11).
  7. state.materialized = target, state.materializing_to = None; write state.
  8. Seed the scan cache for written files (every working-copy write sgit makes does; CHANGELOG 0.26.0 "Fixed — from the newsroom's first morning").

Crash recovery (5.3 order). Any history rebase invocation first calls recover(directory, state): if materializing_to is set, re-run steps 3–7 with the same target. The diff is from materialized (what the disk held before) to materializing_to, and each write is idempotent (a file already at the target content is rewritten with the same bytes; a deletion of an absent file is a no-op), so a half-written working copy converges. If the clone ref already equals materializing_to, step 6 is a no-op.

Selective working copies (clone --no-checkout / --sparse, Pull__Selective): the writer writes only checked-out paths and records the rest. At the end of a pull --rebase, selective.record_pull(final, added, modified, deleted) with the lists from diff_trees(final, orig_head), so sgit checkout --since-pull writes what the rebase brought in.

5.8 Stops

At a stop the engine: materialises tip (5.7), writes what the stop needs, sets stopped_reason, stopped_item, and the remaining todo, and exits 1.

5.8.1 Conflict

  • materialize(tip), then write the merge result for C's clean paths into the working copy (the paths in merged_map that differ from T) through the same writer, so the working copy is "tip + everything of C that applied".
  • Whole-file conflicts: write_conflict_files(directory, conflicts, theirs_map, …) (Vault__Merge.py:82-106): the working file stays the tip's version (ours), <path>.conflict holds C's version (theirs). Marker conflicts (--merge lines): write_marker_files.
  • Merge state (design__01 fields): operation = rebase, ours_commit_id = tip, theirs_commit_id = C, lca_id = P, source_commit_id = C, merge_style, conflict_style, marker_paths, conflict_paths. This makes sgit resolve work unchanged and makes every existing Vault__Merge__State.check_not_in_progress caller refuse (pull, push), with the message adjusted for operation == rebase (5.15).

5.8.2 Edit

C is replayed and committed normally (new created, tip = new), then materialize(tip) and stop. The user may change files. --continue amends (5.9.1).

5.8.3 Reword (non-interactive, no message)

C is replayed and committed with its original message, materialize(tip), stop. --continue -m MSG re-creates the tip commit with the same tree and parent and the new message (an amend of a commit that is not pushed, so no check is needed beyond I1). Interactive mode never stops for a reword: the editor opens on message with the original text, and runs prepare-commit-msg/commit-msg (5.13).

5.8.4 Exec

materialize(tip), then run the argv (5.10, exec). Exit 0: carry on. Non-zero: stop with EXEC_FAILED, record the exit code; --continue carries on without re-running it (Git without --reschedule-failed-exec).

5.8.5 Break, empty, missing blob

break: materialise and stop. EMPTY: 5.5.5. MISSING_BLOB: a sparse/selective clone needed a blob to merge and the server could not be reached: stop with the blob ids listed; --continue retries the same item.

5.9.3 --abort

  1. Remove conflict files of the current stop (if any).
  2. materialize(orig_head) with materialized = the state's value. The working copy goes back on exactly the paths the rebase changed, plus the paths the user edited during a stop on those paths. Files the user edited at a stop on other paths: Git's --abort does reset --hard and discards them. sgit does the same but prints them first (Discarding uncommitted changes: …), because reset already behaves that way (Vault__Sync__Pull.reset, :60-66) and the user asked to abort. To scope the reset, a scan of the working copy against materialized lists the dirty paths, and those paths are added to the rewrite set.
  3. Clone ref = orig_head, reflog reason rebase (abort).
  4. Delete merge state and rebase state.
  5. Autostash: pop (5.12.4).

5.9.4 --quit

Delete the rebase state and any operation = rebase merge state; leave the ref, the working copy and conflict files as they are. The autostash is kept in the stash list and named in the output (Git keeps it too).

5.17 Compatibility

  • No format change, no gate. Every replayed commit is an ordinary commit_v1 object with one parent, a tree built by the same rules, a clone signature and (optionally) a design__02 user signature. Old clients and the web UI read, verify and pull it like any commit.
  • No server change. I2: the rebase writes nothing remote; pull --rebase writes exactly what a merge pull writes; the following push is an ordinary fast-forward.
  • Local files. New fields in config.json, reflog.jsonl and merge_state.json are optional; an older build ignores them (unknown keys accepted) and, if it rewrites config.json, drops pull_rebase, which falls back to merge: fail-safe.
  • An older build during a rebase stop sees merge_state.json and refuses pull/push with the merge message; it does not know operation = rebase and would let sgit commit make a two-parent commit. Acceptable: mixing builds inside one working copy mid-rebase is not supported, and sgit update is the remedy (stated in the CHANGELOG entry).
  • Workflow__Pull (merge) is unchanged byte for byte when rebase is off.

Worktrees (design__06)Each worktree has its own .sg_vault/local/ (state, ORIG_HEAD, reflog) and its own clone branch: independent rebases. New objects go to the worktree's own store per design__06; reads fall through to the main store. Two worktrees rebasing concurrently do not share refs.
Bisect (design__05)Mutually exclusive (5.15).
Hooks (design__03)5.13. --no-verify skips pre-rebase only.
Line merge (design__01)--merge lines gives marker conflicts and clean line merges inside the replay; default stays whole-file .conflict (the agreed default).

8. Performance

Measured costs from the 0.26.0 release-readiness note (76,000 files in 58,553 folders, in-memory host): full clone 61 s, push of a 5-file commit 4.5–5.2 s, history log of 4 commits 0.45 s. Estimates below are per step, from the code paths each step uses; the acceptance list (9.4) requires measuring them.

StepCost driverEstimate on 76k files
Range walkone commit decrypt per commit not yet in the generation memo; then O(range + upstream since base)< 0.5 s for a 50-commit range; first run on a loose vault walks the history once (626 commits ≈ 1 s)
Cherry detectiondiff_trees per upstream commit since the merge base (only differing folders)~10–30 ms per commit; capped at 2,000 commits
Replay of one commit changing k files at depth ddiff_trees (≈ k·d folder loads) + entry_at for k paths (cached spine) + apply_changes (≈ k·d folder rebuilds) + one commit create/sign~20–100 ms for k ≤ 10
Materialisationdiff_trees(target, materialized) + writing the changed filesproportional to files changed by the whole rebase; one write per file per rebase (not per step)
pull --rebasethe merge pull's fetch cost (unchanged) + the abovedominated by the fetch, as a merge pull is

What is avoided. build_from_flat re-encrypts all 58,553 folders per call (4); a replay that used it would cost tens of seconds per commit on this vault. apply_changes rebuilds only the spines. No step builds a full flat map; the only full scan is the clean-tree check at start (the scan cache makes it a stat per file: 6.5 s on the 228,000-file vault, CHANGELOG 0.26.0) and the scan at --continue.

Caps. REBASE_CHERRY_SCAN_MAX = 2000; the line engine's caps are design__01 D8's. A todo longer than REBASE_TODO_WARN = 500 items prints a warning (no refusal).

9. Test plan

All unit tests use real objects: two clones over Vault__API__In_Memory via Vault__Test_Env (fixed test key), no mocks. No __init__.py in tests. File and class names follow the repository convention.

9.1 Planner and todo — tests/unit/core/actions/rebase/

test_Vault__Rebase__Planner.py → Test_Vault__Rebase__Planner:

  1. Linear: 3 local commits, 2 upstream → todo is the 3, oldest first.
  2. Merge commits in the range are dropped; both sides linearised in topological order (the measured Git case: mer1, side1, after).
  3. A local commit equal in effect to an upstream commit (same path, same old and new content hash, different blob ids) is skipped_upstream; with reapply_cherry_picks it is in the todo.
  4. Range when the local named ref and the baseline differ (both excluded).
  5. Explicit upstream HEAD~2 that would include a pushed commit → refused (I1), naming it.
  6. --onto X: replays U..H on X.
  7. --keep-base: onto = merge base; several merge bases → refused.
  8. Up to date; fast-forward case.
  9. Shallow clone: range above boundary works; range crossing a boundary refused with the --unshallow hint.
  10. Foreign commit refused; --allow-foreign admits it; under signatures-required an unsigned foreign commit is refused even with the flag.
  11. Scoped clone: a commit touching an unheld folder refused.
