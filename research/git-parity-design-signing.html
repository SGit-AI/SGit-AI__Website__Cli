1. Summary and the exact Git behaviour matched

Git does not decide who is allowed to write. It signs with the key the user already has, stores the signature in the commit, and leaves trust to whoever verifies. sgit does the same, as an optional second signature next to the per-clone ECDSA signature it already makes.

What stays as it is:

  • The clone key. Every commit keeps its per-clone ECDSA signature (signature, author_key_id). signatures-required keeps meaning "every commit carries a valid clone signature".
  • TM-R01. It is unchanged at vault level. It is closed for any verifier who keeps an allowed-signers file, in exactly the way Git closes it (6.1).

2. Scope and non-goals

2.1 In scope

  • Commits and annotated tags (vault tag create) carry an optional user signature.
  • SSH (all key types OpenSSH signs with, 5.4.3) and OpenPGP via gpg.
  • Settings are read from the user's Git config (global and system), and can be overridden per command.
  • Verification surfaces:
  • history log --show-signature
  • history show --show-signature
  • check verify, extended with a user-signature summary, --require-user-signature and --json
  • vault tag show
  • the --json output of those commands
  • An in-process verifier for SSH signatures. No ssh-keygen is needed to verify; it is needed only to sign with agent or hardware keys.
  • A per-clone verification cache.

3.3 How the attached key form is parsed

CLI__Main.run gets a pre-parse step, CLI__Argv__Signing.normalise(argv):

  • -S<KEY> becomes --gpg-sign-key <KEY> -S
  • --gpg-sign=<KEY> becomes --gpg-sign-key <KEY> --gpg-sign
  • bare -S / --gpg-sign are left as flags (store_true)

--gpg-sign-key is a hidden option, so -S msg keeps meaning "sign, message msg". The step applies only to argv tokens in the commands listed in 3.1, and only when they come before --.

5. Design

5.1 The signed bytes

There is one definition, used by both signatures (clone and user), for commits and for tags:

SIGNATURE_MEMBERS = ('signature', 'user_signature')            # class attribute on Vault__Commit and Vault__Sync__Tag

signing_bytes(d) = UTF-8( JCS( { k: v for k, v in d.items() if k not in SIGNATURE_MEMBERS } ) )
                 = json.dumps(body, sort_keys=True, separators=(',', ':'), ensure_ascii=False).encode('utf-8')
  • d is commit.json() (or tag.json()) of the current schema, which includes author_signature: null and attestations: [] exactly as today. Removing user_signature makes these bytes identical to what every existing client computes. Existing clients never see the member, because their schema drops it (4.1).
  • Legacy form (author_key_id null): legacy_signing_bytes(d) must also drop user_signature before setting signature: None. Otherwise a new client would add "user_signature": null to the bytes and fail every pre-0.19 commit. This is the one easy-to-miss change.
  • Both signatures cover the same bytes. The user signature therefore covers:
  • tree_id and parents (the content and the history);
  • timestamp_ms;
  • message_enc (the ciphertext, which AES-GCM authenticates, so it fixes the plaintext);
  • branch_id and author_key_id (it binds the clone key that co-signed).

It does not cover the clone signature, and the clone signature does not cover it. Either can be checked alone, and stripping one leaves the other valid. That is what Git does with gpgsig and the commit.

  • For SSH, the user signature is an SSHSIG over these bytes with namespace git (D1) and hash sha512 (ssh-keygen's default). For OpenPGP, it is a binary detached signature over these bytes.

5.4 SSH: exact formats and the in-process verifier

5.4.1 SSHSIG layout (OpenSSH PROTOCOL.sshsig)

Blob (what we store, base64 in blob):

byte[6]  MAGIC_PREAMBLE  "SSHSIG"
uint32   SIG_VERSION     0x00000001
string   publickey       (wire-encoded public key; for certificates, the certificate)
string   namespace       "git"
string   reserved        ""   (verifiers ignore its content)
string   hash_algorithm  "sha512" | "sha256"
string   signature       (an SSH signature: string algorithm, then the algorithm's blob)

Signed data (what the key actually signs):

byte[6]  MAGIC_PREAMBLE  "SSHSIG"
string   namespace
string   reserved
string   hash_algorithm
string   H(message)       SHA-512 or SHA-256 of signing_bytes (5.1)

Armor (only for display and for ssh-keygen): -----BEGIN SSH SIGNATURE-----, base64 wrapped at 70 columns, -----END SSH SIGNATURE-----.

Parser rules (every one of these has a test):

  • the whole blob ≤ 6144 bytes after base64 decoding;
  • every string length ≤ the remaining bytes;
  • no trailing bytes;
  • magic exact;
  • version == 1;
  • namespace == the configured namespace (git, D1);
  • hash in {sha256, sha512};
  • the signature algorithm must agree with the key type: ssh-ed25519 ↔ ssh-ed25519; ecdsa-sha2-nistpN ↔ the same; RSA keys only with rsa-sha2-256 / rsa-sha2-512 (ssh-rsa / SHA-1 is rejected, as ssh-keygen does); sk types ↔ the same.

5.4.2 Fingerprints and display

  • The fingerprint is SHA256: + base64 (no padding) of SHA-256 over the wire public-key blob, exactly as ssh-keygen -l prints it.
  • The key type name for display follows ssh-keygen: ED25519, ECDSA, RSA, ED25519-SK, ECDSA-SK.

5.4.4 The allowed-signers file

Format from ssh-keygen(1), ALLOWED SIGNERS section: one entry per line, principals [options] keytype base64-key [comment]. # starts a comment and blank lines are ignored.

  • Principals: comma-separated patterns. * and ? are wildcards, and a leading ! negates (match_pattern_list semantics). A principal matches if it matches at least one positive pattern and no negated one.
  • Options handled in-process:
  • namespaces="git,file": the configured namespace must be in the list;
  • valid-after="YYYYMMDD[HHMM[SS]][Z]", valid-before="…": local time unless Z; compared with the commit's timestamp_ms (5.4.6);
  • no-touch-required, verify-required.
  • Option that forces delegation: cert-authority (5.4.5).
  • principals_for(key, ns, t) returns, in file order, every line whose key equals the signature's public key and whose namespace and validity allow it. When there is more than one, the first principal is shown and the rest are listed in --json.

5.4.5 Delegation to ssh-keygen

SSH__Sig__Verifier__Keygen is used only when one of these holds:

  1. the signature's public key is a certificate;
  2. the allowed-signers file has a cert-authority line;
  3. the revocation file is a binary KRL (magic SSHKRL\n\0).

It reproduces Git's calls exactly:

ssh-keygen -Y find-principals -f <allowed> -s <sigfile> [-Overify-time=<YYYYMMDDHHMMSS>]
ssh-keygen -Y verify -n git -f <allowed> -I <principal> -s <sigfile> [-r <revocation>] [-Overify-time=…]   (payload on stdin)
ssh-keygen -Y check-novalidate -n git -s <sigfile>                                                         (payload on stdin)
  • <sigfile> is the armored signature written to .sg_vault/local/tmp/sig-<random>.sig (0600) and removed in a finally. The payload is ciphertext-derived JSON, but it still goes on stdin, not to disk.
  • Without ssh-keygen, the result is cannot-check, never good.

5.4.6 Time

Commit time is timestamp_ms, chosen by the committer (as Git's committer date is). valid-after/valid-before are checked against it, exactly as Git passes -Overify-time=<committer date>. 6.5 covers what that does and does not prove.

5.5 Running ssh-keygen and gpg

Signing__Command_Runner.run(argv, stdin, timeout, env):

  • Process: subprocess.run(argv_list, input=stdin_bytes, capture_output=True, timeout=…, env=env, cwd=<a safe dir>, close_fds=True). Never shell=True. argv is built from config values as separate list items; nothing is joined into a string.
  • Program: resolved with shutil.which (config value first, then the default name). A config value that is a path is used as is. Not found → code=127.
  • cwd: the user's home directory, never the vault working copy. Neither program reads per-directory config, but this removes any chance that a file in the vault is picked up.
  • Environment:
  • inherited: SSH_AUTH_SOCK (agent), GNUPGHOME, GPG_TTY, DISPLAY/WAYLAND_DISPLAY and SSH_ASKPASS (pinentry and askpass), HOME, PATH;
  • added: LC_ALL=C, so messages are stable for the error text; the gpg status lines do not depend on locale anyway.
  • Timeouts:
  • signing 120 s (a passphrase prompt or a hardware-key touch can take a while);
  • verifying with gpg 30 s;
  • git config 10 s;
  • gpg.ssh.defaultKeyCommand 10 s.

A timeout is a failure with its own message.

  • stdin is the payload, so passphrase prompts go to /dev/tty (ssh-keygen) or to pinentry (gpg), exactly as with Git. With no TTY and no agent, signing fails, and the command fails closed (3.5).
  • Signing argv:

| Case | argv | |---|---| | SSH, key is a private-key path | [ssh_program, '-Y', 'sign', '-n', 'git', '-f', <path>], stdout = armored SSHSIG | | SSH, key is a .pub path | same; ssh-keygen finds the private half in the agent | | SSH, literal key (key::ssh-… or ssh-…) | write the literal to .sg_vault/local/tmp/signing-<random>.pub (0600) and pass -f <that> -U. -U exists from OpenSSH 8.9; on an older ssh-keygen the call fails and the error names the version | | SSH, no key but gpg.ssh.defaultKeyCommand set | run it (shlex.split, never a shell; Git runs it through a shell, a documented difference), take the first line of output starting ssh- or key::, then as the literal case | | GPG | [gpg_program, '--status-fd=2', '-bsu', <key>], stdout = binary signature.   • Output checks:
  • SSH: dearmor, then SSH__Sig__Blob.parse, and the signer verifies its own output in-process before returning (this catches a misconfigured program).
  • GPG: the output must start with an OpenPGP signature packet tag (0x88/0x89/0xC2), with length within the 8 KB cap.

5.6 Configuration resolution

5.6.1 Order (first set wins per key)

  1. Command flags: -S / --gpg-sign[=KEY] / --no-gpg-sign; for tags -s / -u KEY / --no-sign. A key given here also turns signing on (Git: -S<key>).
  2. The user's Git config, global then system (5.6.2): sgit.gpgSign for the on/off switch; user.signingKey, gpg.* for how.
  3. Defaults: signing off; format openpgp (Git's default) unless user.signingKey looks like an SSH key (a literal ssh- or key::, or a path ending .pub or to an OpenSSH private key). Git requires gpg.format = ssh for that; inferring it is a convenience, not a contradiction, because Git would fail on that key with openpgp. Flag D3b.

Repository-level Git config (.git/config of a repository the vault happens to sit in) is not read (D3). Vault content is never read for signing settings: no file in the working copy or the vault can change how or whether sgit signs (6.4).

5.6.2 Reading Git's config

Git__Config__Reader._read_with_git() runs these when git is on PATH:

git config --global --includes --null --list
git config --system --includes --null --list

Both run in the home directory, with Git's own environment honoured (GIT_CONFIG_GLOBAL, GIT_CONFIG_SYSTEM, GIT_CONFIG_NOSYSTEM, XDG_CONFIG_HOME). The output is NUL-separated key\nvalue records. Global overrides system, and within a file the last value wins.

When git is not installed, _read_files() falls back to a small INI reader:

  • Files: $GIT_CONFIG_GLOBAL, else $XDG_CONFIG_HOME/git/config then ~/.gitconfig.
  • Supported: sections, subsections, key = value, quoting, \ escapes, booleans (true/yes/on/1).
  • Not supported: include/includeIf (a warning names them).

The result is cached for the process, and sgit doctor gains a "Signing" block showing each value and its source.

5.9 Compatibility: why no gate is needed

5.9.1 Clients from before this change

  • They read a signed commit without error. from_json ignores the unknown member (tested on the current osbot-utils; 9.5 runs released builds).
  • Their clone-signature check still passes. They compute signing_bytes(commit.json()) from their schema, which has no user_signature. The new client computes the same bytes because it removes user_signature (5.1). The bytes are equal, so verification succeeds.
  • They never write the member back. Commits and tags are immutable content-addressed objects, and no client re-serialises an existing one. The only rewriters (pack convert, migrate, move sentinels) make new commits; old clients would simply not carry the member, and new ones deliberately do not (7.6).
  • Their signatures-required checks see no change, because that policy is about the clone signature.

5.9.2 New clients reading old commits

user_signature is absent, so the status is none. signing_bytes and legacy_signing_bytes are unchanged for these commits, because removing an absent or null member changes nothing. The legacy path needs the explicit removal in 5.1, and a test pins it.

5.9.3 Unsigned commits

They are byte-identical to today's (the member is not written when None).

5.9.4 Two things to confirm before release

  1. The web UI. If the web UI computes the clone signing bytes from the raw stored JSON rather than from its own schema, it will now include user_signature and report a bad signature on user-signed commits. Its rule must become "remove signature and user_signature". The interop vector (5.10) makes that testable for them. Until they confirm, a user-signed commit may show as bad in the web UI. Unsigned commits are unaffected. (D7)
  2. The oldest sgit still in use. The xver run (9.5) must show that released builds (0.19.0, 0.21.0, 0.24.0, 0.26.0) ignore the unknown member.
  • Fallback if any of them rejects it: sign only in vaults whose min_client is at or above the oldest build that tolerates it, and say so by name.
  • Why this is not a gate: it is a refusal to sign, not a format change.

6. Security and threat model

6.1 What TM-R01 becomes

TM-R01 is the attack where any read-key holder with store write access mints a clone key and authors commits that check verify calls verified. After this change:

  • For a verifier with an allowed-signers file (or a GPG keyring with trust): a commit is attributable to a principal only if it carries a good user signature. The forger cannot produce one without that principal's private key. Its commits show none or untrusted, and check verify --require-user-signature fails on them. That is exactly Git's guarantee.
  • At vault level, nothing changes: the vault does not require user signatures, and two verifiers with different files can disagree. That is by design (Git parity). Vault-level enforcement belongs to SGitHub.
  • Threat model text: TM-R01's row gains "closed per verifier for commits carrying a user signature (design 02); vault-level enforcement: SGitHub".

6.2 Key material never enters the vault

  • sgit never reads a private key, with one exception: SSH__Signer__In_Process reads an unencrypted OpenSSH key file that user.signingKey explicitly names, when ssh-keygen is absent (D4). It reads it in memory, never copies it, never logs it, and never caches it.
  • Signing otherwise happens inside ssh-keygen or gpg, which talk to their agents.
  • What the vault stores is the signature, whose SSHSIG form includes the public key, plus nothing else.
  • Suggested follow-up (small, separate): extend the existing secret guard to refuse committing OpenSSH or OpenPGP private key files. Detect -----BEGIN OPENSSH PRIVATE KEY----- and -----BEGIN PGP PRIVATE KEY BLOCK-----, with the existing --allow-secret-file override (D11).

6.3 What vault readers and the host learn

6.4 Subprocesses (TM-R45)

  • Which programs run: they come from the user's global or system Git config, as with Git. Vault content can never name a program:
  • nothing is read from the working copy;
  • repository-level Git config is not read (D3);
  • vault content cannot plant .git/* anyway (TM-F03).
  • How they run:
  • argv lists, no shell;
  • cwd is home;
  • stdin carries the payload;
  • timeouts are bounded;
  • output is bounded by the cap;
  • temporary files are 0600 under .sg_vault/local/tmp/ and removed in finally.
  • gpg.ssh.defaultKeyCommand: Git runs it through a shell; sgit splits it with shlex instead, so shell syntax in it is not interpreted. This is a documented difference.
  • Residual: someone who controls the user's Git config already controls what Git runs. Accepted, the same as Git.

The cache (User__Signature__Cache, .sg_vault/local/user-signature-cache.json, 0600):

  • Key: the commit or tag object id. It is a content address over the ciphertext that contains the signature, so it fixes both payload and signature.
  • Value: the Schema__User_Signature__Result plus a trust_digest. For SSH, the digest is SHA-256 over the allowed-signers bytes, the revocation-file bytes, the namespace and the verifier version. For GPG, it is SHA-256 over the size and mtime of pubring.kbx/pubring.gpg and trustdb.gpg in GNUPGHOME, plus gpg.minTrustLevel.
  • Invalidation: an entry is used only when its digest equals the current one. Editing the allowed-signers file or the keyring invalidates everything at once.
  • Scope: check verify and history log --show-signature use the cache; signing does not.
  • Size: bounded at 200,000 entries. Oldest first out; the file is rewritten atomically.

9.3 SSH without ssh-keygen in this container

  • Signing: SSH__Signer__In_Process signs with real keys generated by cryptography. Ed25519 is deterministic, so it is checked byte for byte against the vector.
  • Cross-check with OpenSSH: the interop vector's armored signature is produced once with real ssh-keygen on a machine that has it, and committed. The in-process verifier must accept it, and the in-process signer must reproduce it exactly (ed25519). This proves byte-compatibility without ssh-keygen at test time.
  • Integration (tests/integration/test_User_Signing__SSH_Keygen.py, class Test_User_Signing__SSH_Keygen): real ssh-keygen sign and verify, -Y verify of an sgit signature outside sgit, delegation for a cert-authority line with a real CA and certificate, a KRL. Skipped when shutil.which('ssh-keygen') is empty. That is a missing-binary skip, not a mock. The CI integration job installs openssh-client so it runs there.
