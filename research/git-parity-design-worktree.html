Design 06: sgit worktree (roadmap 2.13, priority 2)

Status: design, not built. Date: 28 Oct 2026. Roadmap: roadmap__git-parity.md item 2.13, approach A (agreed with Dinis: shared objects only, Git's alternates; no shared refs). Code read at: 3a1d72a on claude/charming-babbage-5hzcxq. Every file:line below is at that commit.

In one paragraph. sgit worktree add <path> makes a second working copy of the vault in seconds, with no network. The new folder is a real sgit clone: its own .sg_vault/local/ (clone branch, signing key, config, caches, merge state, reflog) and its own small .sg_vault/bare/ (branch index, refs, public keys). Its object store has no objects of its own at first. It reads objects from the main vault's store, then from the network, in that order. New objects are written to the worktree's own store and never to the main one. Merging works as today: push, then branch merge. Phase 2 adds branch merge from another local worktree without a push.

2. Scope and non-goals

In scope, phase 1 (2–3 days):

  1. sgit worktree add <path> [--name N] [--branch <named> | -b <new named>] [--path F ...] [--no-checkout] [--vault-key K].
  2. sgit worktree list [--json], remove <name|path> [--force], prune [--dry-run], lock <name|path> [--reason R], unlock <name|path>, dissociate <name|path>.
  3. The read path: Vault__Object_Store reads through one alternate store, verifying each borrowed object by its content address.
  4. Guards in the main vault: vault uninit, vault rekey, vault move, migrate apply refuse while worktrees are registered (names listed, --force or worktree remove first). Guards in a worktree: vault uninit points to worktree remove; vault backup materialises borrowed objects into the zip; a first push of a never-pushed vault is refused.
  5. The working-copy scan never descends into a nested vault (a sub-folder that holds its own .sg_vault). This matters when a worktree is created inside the main working copy, and it fixes a latent bug for any nested clone.

Phase 2 (1–1.5 days): sgit branch merge --worktree <name|path>: merge another local worktree's clone head without pushing. It imports the commits and objects it needs, verified by content address, plus the other worktree's public key, then runs the existing pull merge step.

Non-goals:

Not doingWhy

Sharing the scan cacheIt records paths, mtimes and inodes of one working copy: meaningless in another

3. CLI surface

3.1 Placement (Rule 9) — decision D1

Git has git worktree at the top level, and agents type it from habit. A worktree is about working copies, which are daily-use, not about "the vault as a whole". Recommendation: top-level sgit worktree, with TOP_LEVEL_COMMANDS in tests/unit/cli/test_CLI__B07__Namespace_Moves.py:104 gaining 'worktree' in the same commit (a deliberate edit, as Rule 9 asks). The alternative is sgit vault worktree …. The rest of this section assumes top level. sgit help all (sgit_ai/cli/CLI__Main.py:1491) must list it (it already omits several commands; that list is fixed separately).

Why verify borrowed reads when own loose reads are not verified:

  • the main store is written by another process, non-atomically (store :68, Verified_Write.save :72), so a half-written file is a real possibility;
  • the main folder may be on another disk that changes under the worktree;
  • the cost is one SHA-256 per borrowed object, about 1 GB/s, the same rule kept packs already follow.

A mismatch is reported once per run as a warning (object <id> in the main store does not match its id; fetched from the server instead).

5.4 The write path: new objects go to the worktree's own store

Decision: own store only. Git never writes into an alternate, and the same reasons hold:

  1. Ownership. The main folder's store belongs to the main clone. Two processes writing into one bare/data/ meet the non-atomic writes above and the CAS guard's read-compare (store :70-75), which would raise a false collision on a half-written file.
  2. Removal is clean. worktree remove deletes the worktree folder and everything it created. Nothing the worktree wrote stays behind in the main store.
  3. Kept packs. A --pack-store main has a SQLite table per clone (local/pack-store.sqlite). A worktree writing loose objects into the main bare/data/ would bypass that table's intake rules.
  4. Cost. The duplicate is only what the worktree itself creates or fetches: its own commits, plus what it pulls that the main has not pulled yet.

A pull in the worktree downloads only objects missing from both stores, because exists covers the alternate. When the main clone has already pulled, the worktree's pull downloads only refs.

Reference numbers, 76,000 files in 58,553 folders, in-memory host, 4 cores (10/26/release-readiness__pack-indexes-branch.md §3): full clone 61 s; clone --no-checkout 28 s, so the network and store part is about 28 s and the checkout about 33 s; clone --path raw/c09 (1,520 files) 2.8 s.

worktree add variantWork doneExpected time (to measure, acceptance item A9)

On a real host the gain is larger (a clone's network share was 165 s before the bulk fetch on the DC vault, 80 s after)

PartSize
Working copythe same as any checkout (unavoidable)

Read-path cost for clones without worktrees: one os.path.isfile on local/alternates.json per object-store instance (probed once), so nothing measurable.
