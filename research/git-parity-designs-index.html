Git parity, priority 1 and 2: index, shared foundations and reconciliation (28 Oct 2026)

Date2026-10-28 · 03:19 UTCKinddesignResearch topicsgitWritten bythe sgit-ai CLI team (Claude Code sessions), for Dinis CruzSourceteam/humans/dinis_cruz/claude-code-web/10/28/design__00__index-and-reconciliation.md in SGit-AI__CLI at 036e33b. Published here as written; the CLI repository is where the work happened.

What this is: the entry point to the seven design documents for the Git-parity roadmap (roadmap__git-parity.md). Each document was written against the code at 640069a and ends with an acceptance checklist. This index does three things:

  • it lists the parts several designs need, to be built once;
  • it settles the places where two designs disagree;
  • it collects the bugs found in today's code and every decision waiting on Dinis.

Where this index and a design disagree, this index wins. The designs were written in parallel, and section 2 records the outcome of checking them against each other.

F4Same content on both sides is not a conflict.every merge path: pull, branch merge, revert, cherry-pick, rebase, rewind re-apply01Found independently by 04 and 07 (X1). Blobs use a random IV, so two clones writing the same content get different blob ids. three_way_merge compares ids only, so today it reports a conflict. Fix: when ids differ, compare content_hash and size; if equal, decrypt both and compare bytes (04's verify_exact), then take ours. This changes the default whole-file merge too, so it is decision X-D1 (section 5).

2.1 What is allowed while an operation is in progress (F5)

Git's rules, with one deliberate difference: Git allows push during these operations, but sgit's push runs an implicit pull that writes the working copy, so sgit refuses it (it already does for a merge, Vault__Sync__Push.py:50). "✗" means refused by name, with the way out.

Action ↓ / in progress →merge or cherry-pick conflictbisectrebase (stopped)
commitonly once every conflict is resolved (01 D3, D4)✗ (05 D1)✗: use rebase --continue (07 D8)
write✗✗✗
pull, branch merge, cherry-pick, rebase✗✗✗
push✗✗✗
branch switch / checkout <commit>✗✗ (bisect moves the working copy itself)✗
bisect start✗—✗
stash✗✗✗ (--autostash is rebase's own)
status, log, diff, show, blame, grep, cat, ls✓, and status shows the operation (01's status block)✓✓
worktree add / remove of another worktree✓ (state is per clone)✓✓

Every operation's state lives under that clone's .sg_vault/local/, so each worktree (06) has its own and they never block each other.

4. Implementation order

Each step leaves pytest tests/unit -n auto and pytest tests/security green. Each feature lands with its CHANGELOG entry and any threat-model rows its design lists.

Phase 0: foundations and bug fixes (~4 days)

  1. F8 atomic object writes (B4); B5 nested-vault scan.
  2. F5 operation guard, with B1 and B2 (merge state only at first).
  3. F4 same-content merge (B3), after X-D1 is decided.
  4. F3 tree building (B7).
  5. F1 line differ and F2 commit graph (B6).

Phase 1: priority 1 (~10 days after phase 0)

  1. 2.1 line-level merge, opt-in (01 steps for 2.1).
  2. 2.3 commit <paths> and commit -p, with the push prerequisite B9 (03 steps for 2.3).
  3. 2.2 signing with your own key (02); the signing half waits on the web UI check (02 D7).

Phase 2: priority 2 (~22 days)

  1. F9 pruned diff, then 2.4 renames, 2.5 blame, 2.7 grep (04).
  2. 2.8 cherry-pick (01).
  3. 2.9 hooks (03), then F6 extended by rebase.
  4. 2.12 rebase (07).
  5. 2.6 bisect (05).
  6. 2.13 worktree, phases 1 and 2 (06).

A release can follow each phase. Phase 1 is the "line merges, signing with your own key, partial commits" release.
