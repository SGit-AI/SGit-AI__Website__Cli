The snapshot index of that vault is 52.5 MB with 77,742 members (the folder members for every folder, the cross-references, the commit graph), against a 180 MB snapshot pack: every clone downloads it. The format is the dev pack's; the folder members are what Phase 2's at lives in. If the size matters before Phase 4, the cross-references (blob-paths, file-commits, about a third) can move to an optional member set.

Decisions I took alone, worth a look

  1. A lying index below the root. The reader anchors an index's flat map to the head's root tree (one tree read); a lie below the root in a signed index reaches the working copy with the standing of a commit signed by that key, and pack index verify finds it. Documented in TM-R42 with a Known_Gaps test. The alternative, verifying every folder against its tree, is the walk the index exists to avoid.
  2. sgit checkout <path> is the file verb; sgit branch checkout <target> keeps switching branches. Rule 9 put the daily verb at the top level; the name collides with git's "checkout a branch" only in spirit.
  3. A plain pull on a selective clone writes only the changed files it has checked out and reports the rest ("N changed file(s) not written … sgit checkout --since-pull"). pull --no-checkout writes nothing. A full clone refuses --no-checkout (it would leave the working copy behind the head).
  4. The checkout set is a plain file (local/checkout.json, the paths held; last-pull.json beside it), under the TM-R41 boundary like the flat and scan caches. A sparse clone from before the record keeps the old rule (blob fetched = checked out), which pack vaults cannot use because their packs bring every blob.
  5. The pack store verifies on every read, not only at intake (the dev pack said "first read, remembered"): a hash per read is cheap next to the disk, and it makes T9's flipped byte a certainty. The table holds pack, object id, offset, length: content addresses and numbers, nothing named.
  6. The scoped reader locates objects through each pack's central directory (two ranged reads per pack, cached), not through at: the directory covers commits, older versions and unchanged files in older packs, which at in the head's folder members does not. at is written (and verified) for Phase 4's sgit cat, where the index alone must answer. A host without the presigned route falls back to whole packs and says so.
  7. Path order is on by default for every pack written, since 0.24.0–0.25.0 extract any order; what the host newly learns (which members sit together) is in TM-R42.
  8. Two pushes in one second give pack names that sort by commit id, so "the last listed pack is the newest" is false; three tests assumed it and were fixed to pick by commit. Nothing in the client relies on it (sync_down chooses snapshots by the head), but it is worth knowing when reading listings.

What needs you

  • A dev merge when you want it (I have not merged); a release note draft is the [Unreleased] section.
  • Phase 4 (sgit cat <vault> <path> with no clone; the presigned range on the live API) with the SG/Vault team: the pieces are here (at, read_range, the index reader), the command and its auth are not.
  • /tmp on this machine holds 13,600 sgit-* folders left by test runs (not mine to delete: the cleanup was refused); the disk filled once during a measurement. A tests/unit/conftest.py fixture that removes a test's own vault folders at teardown would stop it growing.
