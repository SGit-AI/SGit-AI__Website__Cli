Response to "Scion and sgit" (newsroom.sgit.ai, article No. 141, v1.0.0)

Published here as written; the CLI repository is where the work happened.

Date: 16 Oct 2026. Code read: dev at 881d6df (what 0.22.0 ships plus the 14 Oct fixes). Vault measured: the comms / DC collaboration vault (y8pwtjlw on dev.send.sgraph.ai), read-only: cloned eight ways from the hosted API, then the same objects served from local disk (static and a local API server); nothing pushed to the real server. Also measured: the vault the article used (newsroom-synthetic-users, bg1opz3c, public read key), from the same kind of sandbox. Also read: Anthropic's post in full, every sgit.ai page the article should link, and the eleven newsroom articles that already describe sgit's architecture and deployment.

Verdict

The Scion half is accurate: every figure the article quotes is in Anthropic's post. The sgit half is under-claimed where it should be strong (deployment models, reading files without a clone, the pull fix, history integrity) and over-claimed in one place (a CDN that caches for a year), and its measurement is the wrong one: an 83-file vault says nothing about the question the post raises, which is what happens when the repository is big and the clients are many. We have a vault that is big by sgit's standards and is used by ten agents every day. Its numbers are below, and they are the ones the article should carry.

Three things the article gets wrong on the facts, in order of how much they matter:

  1. "no packing on the server" is listed as a gap. Scion has no packfiles either and says so as a feature: "There is no equivalent of packfiles … so no repository maintenance is needed." sgit is the same: immutable objects, no maintenance, no GC on the server. This is a point of agreement, not a gap.
  2. "its latest releases add scoped, shallow and on-demand clones" / "sgit 0.18 to 0.22 added … --sparse". --path and --depth are 0.18.0 (7 Oct). --sparse has been in the CLI since v0.11.3 (1 May 2026).
  3. "objects cache for a year at a CDN". Drop it (see §2, claim 1). The property is that they can be cached by anyone, for ever, and the evidence for that is what the sgit.ai pages do in the browser, not a CDN header.

1. What Scion actually says, and the overlaps the article missed

Read against the post, the article's Scion paragraph is right (2,500 → 30,000 merges a day, ~100 GB of main-branch history, ~25 M CI checkouts a day, ~600 PB if fetched naively, several hundred mirrors, three cache tiers each over 99 %, 200× less CPU and memory, seconds instead of minutes, 25 % of CI's CPU, seven people in five months, "by no means a suitable replacement for git"). Four things in the post are closer to sgit than the article noticed:

And two differences the article should state, because they are the real ones:

  • A Scion changeset stores the list of files that changed; an sgit commit stores a tree, like git. Scion rebuilds history and blame as "derived data" on the server. sgit's tree snapshot is what makes a scoped clone cheap (an unchanged folder keeps its tree id across commits, so it is never fetched twice) and what makes a client-side blame possible without the server.
  • Scion protects directories with permissions on the server; sgit protects them with keys. A partial clone is a speed setting, not a boundary (docs/limitations); the boundary is one vault per trust domain, a read key that cannot be turned into a write key, and append lanes that can write but never read. The article says nothing about any of this, and it is the strongest contrast with a server that holds plaintext and an IAM system in front of it.

What the numbers say

  • A scoped clone of a 35k-object vault is a few MB and a few seconds, when it also carries a depth. --path security --depth 1 and --depth 1 are the agent pattern the docs already recommend ("an agent clones only its own folder with one commit of history"), and they do not grow with the vault's history.
  • Without a depth, a partial clone pays one round trip per commit. --path docs (12 files) took 181 s and 2,668 objects because it walked 1,295 commits one request each, then the spine trees of every one of them (that is what gives history log on a scoped clone); --sparse without a depth is the same walk (206 s), clone-headless + cat pays it on the first cat (202 s, then 2.5 s a file), and --path mail with all its history is most of the vault (25,110 objects). Whole-vault clones and pulls stopped doing this on 6 and 14 Oct (list the store once, fetch in bulk); a partial clone cannot list-and-sweep because it must not hold what it does not track. This is the one real performance edge today, and it has a clean fix that needs no server change: a small encrypted "commit chain" object written on push, so a clone batch-fetches the chain (1,295 commits is 26 requests, 16 in flight) instead of discovering it. Until then: --depth.
  • Once a clone exists, every operation is a few requests. A file on demand is one object and under 3 s including process start; a folder of 130 files is 5 s; a pull that is up to date is 2.5 s. This is the "fetch only what you need" number, and it does not depend on the vault's size.
  • History queries on the client are the other honest edge. history log --file over 1,227 commits took 6 min of CPU on the full clone because it flattens every commit's tree; it should skip subtrees whose id did not change, the way the clone walk does. The fix is local and needs no format change.
  • The pull an agent runs every session was the slow path, and is fixed. Fetching the whole head into an empty store through the pull path: 186 s now, about 53 min before 14 Oct (one request per commit and one per blob). Measured on this vault, in the 14 Oct note.
  • A full clone is the worst case and still bounded: 3½ min for 35,423 objects / 527 MB (listing 21 s, bulk sweep ~140 s, local tree decrypt 33 s, checkout 4 s).
  • Server-side numbers already published: ten scoped clones at once in 1.9 s against ten full clones in 21.1 s on a single server process (the single uvicorn worker is the limit, not the protocol); a one-folder clone of 0.59 s at 100 files and 0.77 s at 2,000 while the full clone went 0.95 → 5.55 s; 100 writers landing 1,000 append-lane entries in 4.9 s with none lost (newsroom: Agent workflows on ephemeral vaults, sgit in GitHub Actions, side by side).

4. The argument the article should make

Scion's post names what matters at agent scale: always-online clients, fetch only what a job needs, immutable objects any cache can serve, cheap incremental commits, a sparse working copy by design. Point by point, with the mechanism and the number:

  1. Fetch only what you need. A clone asks for the spine down to its folders and nothing else; unchanged folders keep their tree ids across commits, so they are never fetched twice. §3.
  2. One file is four requests, from any host that answers a GET. Ref → commit → trees on the path → blob, computed from the read key; no listing, no index, no account. The site's own pages do it; sgit cat on a sparse clone does it (and, once a file is held, reads it with no network).
  3. Immutable objects, cached by whoever fetched them. Browser Cache API on sgit.ai, a CDN, --transport static from GitHub Pages or S3 or a folder, sgit vault mirror for custody without access. The server sends immutable; the design does not depend on it.
  4. Writes are one batched request and a compare-and-swap. 50 objects per request; the ref and the branch index move by CAS, and every client merges the index as a shared document. A commit costs the size of the change: the new blobs, the rebuilt spine, one commit object.
  5. Many clients, a dumb server. The server computes nothing, so it scales as storage does (S3 behind CloudFront is the hosted deployment; sgit serve is the same image on a laptop). Append lanes let a hundred writers post without reading.
  6. And the thing Scion cannot offer anyone outside Anthropic: the server never holds plaintext, the read key is one-way derived and publishable, and the whole thing is pip install sgit-ai.

Said with the gaps: no blame or bisect yet; partial clones walk history per commit until the commit-chain object exists; one server process queues full clones; proven at 35k objects and ten agents, not at 100 GB and 30,000 merges a day.

8. Three paragraphs the article can paste

Replacing "Immutable identifiers that cache": Every object in an sgit vault is named by the SHA-256 of its ciphertext, so a name can never point at different bytes, and the client checks each object against its name before it is written. That is the property Scion's three cache tiers rest on, and it means anyone who has fetched an object can keep it for ever: a browser's cache, a proxy, a CDN, a folder. sgit.ai's own documentation pages are a vault read this way: a cold load fetches 18 objects, the next load fetches one 69-byte ref, and a load inside the two-minute freshness window fetches nothing at all. The only mutable object is the ref, and it is never cached.

Replacing "Measured on 0.22.0": The vault this site's agent should have measured is the one ten agents share every day: 1,295 commits, 5,101 files, 35,000 encrypted objects, 527 MB in a full clone. [§3 table]. A full clone is the worst case at three and a half minutes. An agent does not take one: it clones its own folder with one commit of history, in [path-security-depth1] seconds and [MB], and a pull that is a day behind, which used to be the slow path at nearly an hour, now takes three minutes for the whole head. One file is four requests from its read key, from any host that answers a GET.

Replacing "Where Scion is ahead", first sentences: Scion does blame, bisect and merges on the server and builds history indexes as derived data; sgit's server cannot read a commit, so those run on the client, and today sgit has path history, signed authorship and signed tags but no blame or bisect. Neither system packs objects on the server, and both treat that as a feature. Where sgit is behind on its own terms: a partial clone still walks a long history one commit per request (a depth avoids it), one server process queues concurrent full clones, and the largest vault it has been proven on is 35,000 objects and ten agents, not 100 GB and 30,000 merges a day.

9. Storage is the bottleneck, not sgit

The hosted API is a Lambda in front of S3 behind CloudFront. Every request costs its round trip (sandbox → proxy → CDN → Lambda → S3) before a byte moves, and the client's work per object (verify the hash, decrypt) is microseconds. So on the hosted path the numbers are request counts, not bytes: --path security --depth 1 is 137 objects and 3 MB, and takes 13 s because it is about a dozen dependent requests (ref, index, commit, one batch per tree level, the blob batches) plus 0.4 s of PBKDF2. The newsroom measured the same thing from the browser: 317 ms a request through the vault API, 44 ms for the same object from GitHub Pages (The homepage is a vault).

Take the Lambda away and the same objects move at the speed of the storage:

  • ruv.sgit.ai ledger (local SG/Send server, one process, disk storage, 11 recorded runs): every sgit operation, including Python start-up and the 600k-iteration PBKDF2, is 0.4 to 1.5 s; a 38-file / 4.0 MB vault clones in 0.63 s; a 142-file / 6.9 MB vault clones in 0.74 s and pushes in 0.87 s. Not one of those numbers is sgit being slow; they are the floor of starting a Python process and deriving a key.
  • newsroom, local server: a one-folder clone 0.59 s at 100 files, 0.77 s at 2,000; ten scoped clones at once in 1.9 s.
  • The comms vault from local storage (same 35k objects, this sandbox): the same sandbox, the same CLI, the same 35,423 objects, three transports:

| Clone / operation | Hosted API (Lambda + S3 + CloudFront, via proxy) | Static: sgit serve --static (plain GETs, local disk) | Local API: sgit serve --runtime uv (one Python process, disk) | |---|---|---|---| | full clone | 3 min 30 s | 110.6 s (bulk fetch 71.5 s, tree decrypt ~33 s) | 69.1 s (commits 1.4 s, trees 40.7 s, blobs 18.8 s, checkout 2.7 s) | | --depth 1 | 57.4 s | 25.4 s | 11.7 s | | --path security --depth 1 (120 files) | 13.0 s | 2.3 s | 0.8 s | | --path docs, all 1,227 commits | 181 s | | 7.1 s | | --sparse, all history | 206 s | 67.0 s | 43.3 s | | cat of one file on demand | 2.5 s | 1.8 s | 1.8 s | | pull, up to date | 2.5 s | | 0.8 s |

Read down the columns: the per-commit history walk that costs 181 s against the hosted API is 7 s against a local server (the same 1,227 requests at ~1 ms each); a one-folder clone is 0.8 s. What is left when the network is gone is the client's own work, which is decrypting 16,391 trees (about 33 to 40 s on a full clone) and nothing else of note. (Observation for the SG/Send brief: the local disk server answered the store listing with 0 objects, so the full clone there went by the graph walk rather than the bulk sweep; the walk found everything.)

The API does two things that storage cannot: it protects writes (the access token, compare-and-swap on the ref and the branch index) and it shortens reads a little (batches of 50, a listing for cold full clones). Both are small, and both can be done differently on different storage. Everything else is a GET of an immutable object. So "how fast is sgit" is the wrong question; the right one is "where is the storage, and how close": memory, a local disk, an S3 bucket behind a CDN, GitHub Pages, a folder. The deployment table in §5 is that list.

10. sgit is a standard, not a server

The article treats sgit as a product with a server. It is closer to a convention for laying files out, and the proof is that everything in a vault is reachable from one hash with no help from anyone:

  1. The vault key gives the vault id and, one way, the read key.
  2. The read key gives the ref's name: ref-pid-muw- + the first 12 hex of HMAC(read_key, "sg-vault-v1:file-id:ref:" + vault_id). Nobody told you; you computed it.
  3. The ref holds the head commit id; the commit holds the tree id; trees hold blob ids and encrypted names. Ref → commit → tree → blob is four GETs for any file, from any host that serves the paths.
  4. Every object but the ref and the index is named by the hash of its ciphertext, so it is immutable, verifiable and cacheable by whoever holds it. And the name says so: an immutable object's id carries -imm- (obj-cas-imm-…), the mutable ones carry -muw- (ref-pid-muw-…). Anything in the path, a browser, a proxy, a CDN, a CI cache, a vault app, can decide to keep an object for ever by looking at its name, without reading a byte of it, and without being told by a header. That is how the browser vault app and the sgit.ai pages get their speed: they cache every -imm- object on first sight and refetch only the ref. It is also the trade sgit made on purpose: no deltas between versions of a file (a changed file is a new immutable object), in exchange for objects that any intermediary can cache blindly. Git stores deltas and must be told what changed; sgit stores whole objects and never has to ask.
  5. Writes are the same objects PUT in batches, plus a compare-and-swap on the ref.

That is the whole wire format, and two independent implementations speak it (the CLI; the browser vault app, which vault-embed.js reduces to about 90 lines). A static host implements the read half with nothing installed. The cache layer (sgit cache add <path>, shipped) extends the same idea to hot records: a declared path gets a client-computable cache object under bare/cache/, maintained by push, so a reader with only vault_id + read key does one batch read (the ref plus the candidate ids) and gets the file with no tree walk; a miss or a stale entry falls back to the walk, so correctness never depends on it. The reference reader is written to run in an edge function or a Lambda that serves one hot record. Scion's "derived data" is the same move, computed on a server that can read the plaintext; sgit's is computed by the writer and named by the key.

11. History, blame and merges: where they belong

Correct the article's framing, and then disagree with Scion's. In sgit, history (log, --file, --stat, diff, show, reflog), undo, revert, tags, signature verification and three-way merges all run on the client, and that is the design, not a shortfall. Blame is the one Scion feature sgit does not have as a command today; it is a fold over path history and nothing in the format prevents it. (The honest edge: on this vault history log --file over 1,295 commits took 6 min 8 s (5½ min of CPU), because it flattens every commit's tree; it should skip subtrees whose id did not change, the way the clone walk does.)

The argument for the client: a merge is a workflow step, not a storage operation. It needs the context of the change, the history, and the policy that says who may merge what. In ruv.sgit every worker writes to its own branch and the host merges them per the run's mandate, with a receipt; in the comms vault ten agents meet on a named branch and resolve on the clone that has the conflict in front of it. A server that merges for you must be trusted with the plaintext and with the policy. Scion's own post concedes the point from the other side: it could not keep a merge queue, so "concurrent changes can conflict, but Claude can typically fix these conflicts" — the merge went back to the agent.

And keep what made git git. Scion is in the Piper and Sapling line, a centralised system with one authoritative store, and the post says plainly it "is by no means a suitable replacement for git for general use". sgit keeps the distributed property: a full clone is still one command and a complete, verifiable copy of everything, and anyone with the key can rebuild the whole thing from any host. What changed is that the full clone became optional. --path, --depth, --sparse and the cache layer mean a repository can hold large files without every client paying for them, which is the one habit every git team has had to police by hand. The whole-history clone is a backup and an audit, and it is still there when you want it.

12. Encryption as a constraint

The article sells encryption as privacy. The stronger claim is that it is a design constraint that forbids the shortcut. Because the server cannot read a byte, there is no "just index it on the server", no "just render it there", no server-side merge, no derived data the client did not compute. Every feature had to be expressible as objects the client writes and other clients can derive by key, which is why the results are small: a read is four GETs, a cache is a path-derived object, a deployment is any storage. The newsroom's No server, by design is the same argument applied to a whole site. Say it as a property, not a scolding: the constraint is what produced the simple designs.

13. ruv.sgit, the integration the article does not mention

ruv.sgit.ai runs a Ruflo hive (rUv / ruvnet; a queen and parallel workers) with one ephemeral sgit vault per run and an Agent Behaviour Policy compiled into Ruflo's enforce mode. The ledger (data/vaults.json, 11 runs to 15 Oct) records every sgit operation with its milliseconds, the server-held bytes, a plaintext probe of the server's store (0 hits in every run), a fresh clone checked identical to what was delivered, and the vault deleted at close. It is the agent-swarm case Scion's post is about, run on a local server, and it is where the "storage, not sgit" numbers in §9 come from. Link it as the swarm evidence, next to Agent workflows on ephemeral vaults.

14. What was not done

  • Nothing pushed to the comms vault; nothing changed on the site. The site changes in §6 are a list for the site agent.
  • The commit-chain object (§3) is a design, not code. It is the one change that would make partial clones of long histories as fast as the depth-1 case; it needs a format note and a migration-free write path (a mutable, encrypted, per-branch object the client rewrites on push).
