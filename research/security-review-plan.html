Plan — the next security review of sgit-ai, with skills, and the review graphs it produces

Date2026-10-11 · 16:32 UTCKindplanResearch topicssecurity-reviewWritten bythe sgit-ai CLI team (Claude Code sessions), for Dinis CruzSourceteam/humans/dinis_cruz/claude-code-web/10/11/plan__security-review-with-skills.md in SGit-AI__CLI at 6702521 (branch claude/charming-babbage-5hzcxq, not yet merged to dev). Published here as written; the CLI repository is where the work happened.

From: the sgit-ai CLI agent · Date: 2026-10-11 · Status: proposed, for Dinis to accept or redirect before step 0 runs. Companion docs: research__security-review-skills.md, research__threat-modeling-tools.md, map__security-work-already-done.md in this folder.

1. One sentence

Run a tool-assisted, data-producing security review of one slice of sgit-ai (the code the zero-knowledge guarantee and the trust boundaries live in), using five skills and three tools chosen in the research docs, join every output to the existing register and its tests, and leave behind the first review/ graphs and per-file security records, so the case study can say which tool found what.

2. Scope: the slice, and why it is this one

The code-review-graphs brief says not to start an existing repository with a full derivation, and the secrets.sgit.ai/review/ page starts from what people actually walk. For a security review, what people walk is the key path: derive a key, encrypt, send to the host, verify what comes back, write to disk. Everything the register's High-impact rows touch is in these packages.

4. The steps

Each step names its output. Outputs that are data go under review/ (new, at the repository root, per the brief); prose goes under this folder's date; threat-model changes go in the register with their tests, as §9 of the threat model requires.

Step 0 — Vet, pin, canary (half a day)

  1. Clone each skill source at a commit SHA; record SHA and sha256 of every SKILL.md.
  2. Run skill-scanner scan-all --format sarif over the lot; HIGH blocks install. Keep the SARIF.
  3. Fill the AST10 table from research__security-review-skills.md §2 for each skill.
  4. Install into this cloud session only (no vault key, no token, no .env on disk here): Trail of Bits plugins (audit-context-building, insecure-defaults, sharp-edges, differential-review, post-patch-validation, fp-check, static-analysis, supply-chain-risk-auditor); Sentry security-review, secret-serialization, gha-security-review; stride-threat-modelling skill copy; threat-led-triage skill; pip install stride-gpt==<pinned> with hashes; Semgrep, Bandit, pip-audit pinned.
  5. Rule for every run: the agent never reads .sg_vault/local/*, never prints a key, never runs a skill's "fix" mode. Written at the top of the session prompt.

Output: …/10/11/case-study/00__vetting.md with the table and SARIF.

Step 1 — Context and the first derived graph (one day)

  1. audit-context-building over the slice → audit-context/DOSSIER.md and one file per function. Read the "nothing found" assumptions first; they are the candidate threats.
  2. A small ast-based deriver (classes, methods, calls within the slice, tests that import each module) → review/graph/{files,classes,methods,tests}.json, each node with path, lines and tree hash, per the brief's grammar. Freshness checked by tree hash. Parsers only.
  3. Intent for the slice, written from the threat model's §2 assets, §4 boundaries and §5 mechanisms, each node citing its section → review/intent/boundaries.json, mechanisms.json. This is the top-down half, and it is small because the register already is the intent.

Output: the dossier; review/graph/ and review/intent/ seeds; review/README.md with counts written by the deriver, not by hand.

Step 2 — Threat model, two ways, plus the insider overlay (one day)

  1. stride-gpt analyze <slice> -f json -o review/stride/stride-gpt.json with the cost estimate recorded first. Also -f sarif for the triage step.
  2. This agent runs the stride-threat-modelling skill over the same slice and the dossier → review/stride/agent.json, same schema (id, STRIDE class, component, description, evidence line, mitigation).
  3. Reconcile → review/stride/join.json: each threat id ↔ TM-R/TM-F row ↔ test file, or new, or out-of-scope-by-model (the host-and-harness threats). Disagreements between the two passes are kept, not averaged (the house two-modes rule).
  4. Insider overlay: confirm the thirteen mappings in the threat-modeling doc §1.1 against code; add actor A9 (the agent holding the key) to the register §3, and a column to §6 naming the insider threat ids each row answers. Where a mapping proves an open gap, write its Known_Gaps test in the same commit.

Output: review/stride/ (three files); a register change with tests; the first number for the case study (STRIDE GPT's completeness and coverage against the register).

Step 3 — Code review (two days)

Run in this order, each writing findings as VULN-### / VERIFY-### with file, line, evidence:

  1. Semgrep, Bandit, pip-audit → review/findings/semgrep.sarif, bandit.json, pip-audit.json. These three also become the CI baseline: a new job step in "Run Security & Adversarial Tests" that fails on new findings only (closes TM-R21's open half).
  2. insecure-defaults and sharp-edges on crypto/ and storage/.
  3. Sentry security-review on the slice with the cryptography, file-security, supply-chain and logging guides; secret-serialization on crypto/Vault__Secret_File.py, secrets/, cli/CLI__Debug_Log.py, cli/CLI__Vault.py, cli/CLI__Credential_Store.py.
  4. differential-review on git diff 0.20.0..0.21.0 -- <slice>; post-patch-validation on the TM-F25→F29 and TM-F27→F30 pairs specifically (the two fixes that regressed).
  5. gha-security-review on the three workflows; supply-chain-risk-auditor on osbot-utils and cryptography.
  6. /security-review on each fix commit as it is made (step 4), as the PR gate.

Output: review/findings/<tool>.json per tool, same record shape, each with tool, confidence, file, line, evidence.

Step 4 — Triage and fix (one day, plus the fixes)

  1. fp-check over every finding; a finding without a reproducing path is VERIFY, not VULN.
  2. threat-led-triage rank review/findings/*.json against review/stride/stride-gpt.json → review/findings/ranked.json, with the "could not determine" list kept.
  3. House rule applies to anything real: a Fixed test that fails on the current code, the fix, the register row, the CHANGELOG line, in one commit. Anything accepted gets a Known_Gaps test and a risk_decision with owner and rationale.

Output: fixes with tests; register updated; the per-tool true/false-positive counts for the case study.

Step 5 — Per-file records and the skill rule (half a day)

  1. One .security.json per file in the slice (house schema: attack_surface, vulnerabilities with risk_decision, secrets_exposure, dependencies with trust_boundary_crossings, redundant_code), written from the dossier and the findings, every claim with a line → review/security/<path>.security.json. The slice is 41 files; that is the whole point of the slice.
  2. Add to library/skills/sg-send-cli__SKILL.md (and the sgit skill on skills.sgit.ai) the rule Varlock states and the insider model's I4 needs: never print, echo or log a vault key, read key, write key or token; read keys from the store, not from argv; prefer the key prompt. This is the one thing from the screenshot list that becomes a line in our own skill.

Output: review/security/; the skill change.

Step 6 — Publish (half a day)

  1. The two research docs → skills.sgit.ai and threat-modeling.sgit.ai Documents, as they are.
  2. The case study: which tool found what (true positives, false positives, time, cost per tool), STRIDE GPT scored on the four TM-Bench dimensions against the register, the insider overlay result, the vetting table and the signature gap → both sites, and to Matt Adams.
  3. Link the 0.21.0 register and the case study from sgit.ai/security/ (closes "being prepared").

5. Acceptance

  • Every file in review/graph/ is regenerated byte-identically by the deriver from the tree hash it names; a stale file fails the check.
  • Every STRIDE threat in review/stride/join.json resolves to a register row with a test, or is marked new with a VERIFY, or out-of-scope-by-model with the reason.
  • Every VULN has a test that fails on the code before its fix; every accepted gap has a Known_Gaps test and a risk_decision.
  • The security CI job runs Semgrep, Bandit and pip-audit against a committed baseline and is green on the head that adds it.
  • Suites on the final head: unit, security, integration, QA all pass, with counts in the note.
  • The case study reports per-tool counts, not impressions.
