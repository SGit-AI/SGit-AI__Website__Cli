Agent skills for security review — what exists, what it would do here

Date2026-10-11 · 16:32 UTCKindresearchResearch topicssecurity-reviewWritten bythe sgit-ai CLI team (Claude Code sessions), for Dinis CruzSourceteam/humans/dinis_cruz/claude-code-web/10/11/research__security-review-skills.md in SGit-AI__CLI at 182cfc1. Published here as written; the CLI repository is where the work happened.

From: the sgit-ai CLI agent · Date: 2026-10-11 · For: skills.sgit.ai (Documents), then the case study once used.

Method. Each entry was checked at its source (the repository README or SKILL.md, the project site, or the registry page) on 2026-10-11, not from the aggregator listing that surfaced it. Where a claim could not be confirmed it says so. "On this code" means the sgit-ai CLI: 469 Python files, Type_Safe throughout, two runtime dependencies (osbot-utils, cryptography), AES-256-GCM / PBKDF2 / HKDF / ECDSA P-256 in sgit_ai/crypto/, a host boundary in sgit_ai/network/api/, a local boundary in sgit_ai/storage/.

The ranking rule. A skill earns a place on this review if it does one of three things the existing work does not already do: (a) brings a method (not a pattern list) that reaches crypto, trust boundaries and file handling; (b) brings a tool with deterministic output (SARIF, JSON) we can join to the threat model; (c) vets the other skills. Skills that only restate OWASP web-app lists score low here: this code base has no HTML, no SQL, no sessions.

2. What the vetting gate looks like (AST10 applied)

For every skill the plan installs, record this table in the case study before the first run:

Check (AST10 checklist)Evidence we can produce today
Provenance: author identity, content hash, signatureRepository and commit SHA pinned; sha256 of each SKILL.md recorded; no signature exists for any of them
Scan statusskill-scanner scan-all <dir> --format sarif output kept under the case study; HIGH fails the install
Permissions: files, tools, networkRead from the frontmatter (allowed-tools); Sentry's security-review declares Read, Grep, Glob, Bash, Task. Any skill that fetches remote instructions at run time fails AST05 unless pinned
Identity filesDoes it ask to write CLAUDE.md, AGENTS.md, memory? Sentry's agents-md does by design; the review skills must not
External contentmcp-stride-gpt hosted at mcp.stridegpt.ai sends the app description off-machine; use the skill copy or self-host on loopback (see the threat-modeling doc)
Dependencies pinnedstride-gpt from PyPI pinned by version and hash; the scanner itself pinned
Risk tier matches scopeA review skill that only reads is Low; anything that writes fixes is Medium and runs with --dry-run or not at all
Canary runFirst run in a session with no vault key, no .env, no token on disk (this cloud environment qualifies: find / -name .sg_vault is empty)

The honest finding for skills.sgit.ai: the ecosystem's best security-review skills cannot pass their own community's checklist, because nobody signs skills yet. The skills.sgit.ai thesis (skills as packages with version, permissions and provenance) is exactly the missing piece, and this review is a worked example of the gap.

3. Two ideas worth taking, not installing

  • Confidence tiers with a "needs verification" list (S1). Our house rule already demands a test per finding; the Sentry format gives the step before the test a name. Adopt the VULN-### / VERIFY-### split in the review output, then promote a VERIFY only when its test exists.
  • Context before verdicts (S8 audit-context-building). The dossier's "assumption with nothing found to establish it" is the single most useful intermediate artefact: it is a candidate threat with its line number attached, before anyone has argued about severity. That is the .security.json row's attack_surface and trust_boundary_crossings fields, written by an agent with a citation, which is what the code-review-graphs brief allows at the explanation layer.
