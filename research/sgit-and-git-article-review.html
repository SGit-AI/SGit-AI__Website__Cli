Dinis Cruz passed it to this site on 28 October 2026; it is now also in the CLI repository, at team/humans/dinis_cruz/claude-code-web/10/28/ on dev (036e33b), and led to the Git-parity roadmap. cli.sgit.ai's build agent checked three of its claims against the PyPI release 0.26.0 on 28 October and found all three hold: sgit write leaves other edits uncommitted, a zip holding a vault key is refused at commit, and a pull refuses a rewound head that the host accepted (the script). Review: "What sgit does that Git does not" (newsroom.sgit.ai, article No. 308, 27 Oct 2026)

Date2026-10-28KindreviewResearch topicsgitWritten bythe sgit-ai CLI team (Claude Code sessions), for Dinis Cruz

Article: https://newsroom.sgit.ai/articles/what-sgit-does-that-git-does-not.html (.md twin read in full). Checked against: this repository at 640069a (branch claude/charming-babbage-5hzcxq, the same code as dev): the source, sgit --help for every command group, CHANGELOG.md, the threat model (team/explorer/appsec/threat-model/v0.21.0__threat-model.md) and the response and release notes under team/humans/dinis_cruz/claude-code-web/10/. Numbers that come from the newsroom's own briefs or from cli.sgit.ai pages are not in this repo. They are marked "external": not contradicted, just not checkable from here.

In one paragraph. The article is accurate on the whole, and its honesty sections are mostly fair. There is one headline number we cannot source: "29 minutes to 4.6 seconds" for a one-file commit on a 76,000-file vault. The "commits signed since 0.19.0" line is wrong the other way: commits were signed long before October, and 0.19.0 added verification. Two claims are too strong, both in sgit's favour:

  • "sgit's signatures say which clone wrote a commit" (see TM-R01).
  • "every index is verified against a signed commit" (see TM-R42).

The article also undersells sgit. It does not claim we lack shallow clones: it lists them under "Git has it too", which is right. But it says sgit refuses partial commits (sgit write does them), and it puts "read one file with no clone" wholly in the future (it works today on normal vaults). It also leaves out several things Git has no equivalent for, listed in section 2.

Almost everything on the "Git is ahead" list can be built client-side, as Git builds it. The things that cannot be built are the ones that need the host to read content, and one more: taking back data a reader already has.

What Git has no equivalent for

#Article saysVerdictWhat the code says
16Contents, file names, commit messages and branch names are encrypted; host sees sizes, timing, counts and, in pack mode, which commit each push carried✓ ~Correct, but the leak list is short. The host also sees:
• equality of trees through deterministic tree encryption (KI-SEC-02);
• with blob-deflate, each file's compressibility (TM-R40);
• index pack sizes;
• in path-ordered packs, which blobs share a folder;
• for a scoped clone, which byte ranges it reads, which reveals folder sizes and positions (TM-R42).
17A read key is derived from the vault key one way, so it can never become write access; works from any static host with no account✓ ~Read and write keys are two independent PBKDF2-SHA256 derivations (600k iterations, distinct salts) from the vault key, and neither yields the other. --transport static reads from any GET host. Qualifier: reading is a capability; writing is a permission. The write key is a bearer secret the host checks, with no cryptographic role. A read-key holder with store write access (a host that does not check, or a leaked write key) can author history that check verify calls verified (TM-R01, the top accepted risk).
18Read access cannot be revoked after the fact; per vault, not per folder; "a partial clone is not an access boundary"✓ ~TM-R12. Add the remedy we do ship: sgit vault rekey / sgit vault move rotate the key going forward, and the old vault should be deleted after a rekey. Git and GitHub cannot revoke an existing clone either.
19Append lane: write without read, answer {"ok": true}, a server feature with no sgit command yet✓No append-lane code in sgit_ai/.
20Fetch one folder by byte ranges from plain storage, each object verified by hash✓Phase 2 ranged scoped clone, 0.26.0. Git uses ranged requests only to resume dumb-HTTP downloads. Its partial clone needs a smart server.
21Indexes shipped by the writer, signed and encrypted, checked against the commit and its signature; "a bad one is skipped"; "an index is a plan, never a proof"✓ ~Vault__Pack_Index__Reader order: header → signature under the vault's policy → anchor to the local commit → member sha256. Two qualifiers (TM-R42):
• An unsigned index is accepted unless the vault has signatures-required.
• The snapshot index's flat below the root is not checked by the reader. A signing teammate can mislead a fresh clone's working copy, just as a commit from that key could. sgit pack index verify catches it. Workflow 4's "every index is verified against a signed commit" should say "anchored to its commit and checked under the vault's signature policy".
22sgit pki encrypt --recipient seals a file to a public key✓ ~It writes a sealed file that you then commit. The vault does not hold per-recipient files as a native object type.

2. What we have that the article misses or says we lack

Things the article says we lack, or puts in the future:

  • Partial commits (row 28): sgit write … --also … --push --json. It commits named files atomically to HEAD and, with --push, publishes them in one call. That is the agent form of git commit <paths>.
  • One file with no clone (row 33), on a normal vault: the browser reader does it today (four GETs plus one per folder level), and sgit cache add makes it one batch request. sgit history log --vault-key … already runs with no clone; cat does not yet (section 3).
  • Key rotation: sgit vault rekey and sgit vault move (rotation plus an optional move to another server). GitHub has nothing to rotate; a leaked Git deploy key is revoked on the server.
  • Search / history tools (row 32): history log --grep --since --until --author --file --patch --stat --json, history diff A..B, history show, history reflog, history undo, history revert, history reset, commit --amend, vault stash, signed vault tag, resolve, merge-abort.
  • Shallow and partial clones: clone --depth N, fetch --unshallow, clone --path, fetch <folder> (widen), clone --sparse, clone --no-checkout, clone --bare, clone-branch, clone-headless, clone-range. The article files these under "Git has too", which is fair; we are not behind there.

Things Git has no equivalent for that the article leaves out (candidates for its first list, or for the follow-up article):

  1. Custody without access: sgit vault mirror copies a published vault you cannot read, keyless, and verifies it. A backup service or a second host can hold and check the vault and learn nothing.
  2. Policy carried by the repository and enforced at clone and pull: the format gate (min_client, features) and signatures-required live in the encrypted branch index, and every sgit client enforces them before writing anything. Git's signature checks are each user's local config; a repository cannot require them of its cloners.
  3. Rewind detection on every clone: a remote head that does not descend from the last accepted one is refused by name (pull --accept-rewind to take it). Git's default + refspec takes a forced update with one line of output.
  4. A secret guard: commit refuses vault keys, key-bearing zips and in-tree symlinks to secrets (TM-F11, TM-F18, TM-F27).
  5. Agent-shaped writes: write --push --json and checkout --since-pull. Two scoped agents can never conflict (already in the article).
  6. Serving: sgit serve runs the vault UI and API locally in a container; sgit serve --static and sgit publish lay a vault out for any static host. A read-only clone from a published read key needs no account and no server code.
  7. A computable cache: sgit cache add <path> puts a fixed-cost read of a hot file at a location only key holders can compute, for edge functions. Git has no read path that skips the tree walk.

4. What is impossible, or only partly possible, under zero knowledge

These are limits of the model, not of effort. Each one has a client-side substitute.

  1. Anything the host must read to do. Server-side search, diffs rendered by the server, a "merge" button the host executes, code scanning by the host, server-side blame or language statistics. All impossible unless the host is given the read key, at which point it is no longer zero-knowledge. Substitute: do it in the client or the browser, or in a runner the key holder controls.
  1. Taking back what a reader already has. No system can revoke data already fetched. GitHub cannot either: a removed collaborator keeps their clone. What sgit can do is rotate forward (rekey, move), delete the old vault (TM-R12), and with per-folder keys limit what each reader ever received.
  1. Per-folder permissions enforced by the host inside one key. The host cannot tell folders apart, and anyone with the key can decrypt every object. Per-folder access needs per-folder keys (section 3), not permissions.
  1. Hiding all metadata. Sizes, timing, counts, which ranges a scoped clone reads, and compressibility with blob-deflate (TM-R08, R38, R40, R42). Padding to size buckets, fixed-size packs and decoy range reads reduce the leak, at a bandwidth cost. They never remove it (that would take an ORAM-style protocol).
  1. Host-side optimisation of the store. git gc and repacking on the server, deltas the host computes, dedupe across vaults. The host has only ciphertext. Client-side deltas and prune are possible (section 3). Cross-vault dedupe would need convergent encryption, which leaks equality, so we should not want it.
  1. A host that enforces fast-forward-only. The host cannot read the ref, so it cannot check ancestry. The client-side rewind guard (shipped) is the answer. A signed, append-only ref log kept by the host would let clients prove a rewind, but not stop a write-key holder from making one.

Everything else in the article's "Git is far ahead" list (merges, staging, blame, bisect, search, identity, GC, deltas, IDE support, and most of review and CI) is client-side in Git and can be client-side in sgit. "Twenty years of maturity" is the one item only time fixes.
